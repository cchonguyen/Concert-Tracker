# Lookup pipeline

Part of [ARCHITECTURE.md](../../ARCHITECTURE.md).


A lookup is a `LookupJob` that moves through stages, saving after each one (`src/server/lineup/pipeline.ts`).

1. **Create.** From the app, a lookup starts on a saved event (`POST /api/events/:id/lineup`): its name, year, dates, venue and city become the input, an optional lineup URL can be added, and the job keeps the event's id (`LookupJob.eventId`). Event name and year are required. The edition key is `series-slug/<start date>` when the date is known (an artist plays many nights a year, each with its own openers), otherwise `series-slug/year`. If a confirmed edition with at least one act exists under that key, or under the year key with the same start date (editions confirmed before dates were part of the key), the job is ready for review immediately (`candidate.cached = true`). A verified edition with no acts is not a cache hit: the lookup runs (issue #452). **Paste run** (`docs/specs/pasted-set-times.md`, owner only): pasting a set-times page and its link on an event starts a job that runs only the `pasted` adapter. No other adapter, no reader model and no web search run, so it takes no quota and is never parked on a limit; it goes straight to review, where acts already on the edition gain the pasted times. On the event's Full lineup card the owner opens "Paste set times from a page" (events with a full date only, `src/components/PasteSetTimes.tsx`), which previews what was read and what was not before sending. The same box is on a shared edition in Global Editions (owner, `paste-sets`), where the result waits under Lookups.
2. **collect.** First wave (Clashfinder, promoter, Ticketmaster) runs in parallel. The second wave (setlist.fm) runs with dates and city filled in from the first. Every response is stored as a `SourceDocument`; every act as a `PerformerClaim`. A failing adapter is logged and does not stop the others, with one exception: when the series already has a Clashfinder edition stored for this year (`clashfinderSlugs`) and reading it fails, the job is retried with the normal 3-attempt backoff instead of building a lineup without Clashfinder's stages and days. That check runs before anything from the run is saved, so a retry never stores the other sources twice. The Clashfinder adapter itself asks once more when a 200 response is not valid event data.
3. **extract.** Gates run first, in code: when Clashfinder gave 5 or more acts, no promoter or archived page goes to the reader (`skipped: clashfinder_enough`); a page goes to the reader only when the non-model sources together gave fewer than 2 acts (`skipped: structured_enough`); a page over the input ceiling is skipped with a note (`input_too_large`). Each skip is a line in the job log. Each remaining unstructured document (promoter or archived page) gets one call through the guarded reader (`src/server/reader/`): spend guards and the circuit breaker run before the call, and one `ai_calls` row is written after it (no page text). The defaults (`src/server/reader/config.ts`) are `READER_WINDOW_CHARS` 30000 and `READER_MAX_INPUT_CHARS` 30000: a page is sent whole, and a page over 30,000 characters is skipped with a note (`input_too_large`) and never cut up. A reply that is not valid JSON (`invalid_json`) drops that page with no retry; the next page is still read. A job over its call cap (`READER_MAX_CALLS_PER_JOB`, 6) parks only that job, and an open breaker or a spend guard parks the job with a retry time; nothing falls back to another model or to heuristics. The prompt includes one confirmed example from the same website when one exists. Names failing the verbatim check are dropped and counted in the log. Progress is saved per page, so a quota pause resumes where it stopped. Extraction cache: when an earlier job for the same edition key already read the same document (same URL and content hash) with the same model and prompt version, its claims are copied to the new job, each re-checked with `isVerbatim`, and no reader call is made (`findExtractedClaims`). A page whose text changed is a new document and is read again; a new prompt version reads everything again.
4. **discover.** When there are no claims at all, or when claims are sparse (< 5 acts) for a multi-day festival: one web search (`"<event>" <year> lineup`). Up to 6 results are fetched; a page is kept only if its own text names every word of the event and the year, which drops other editions and unrelated pages. At most 3 kept pages go to extract. A result on the event's own domain (its host contains the event name run together, e.g. `sunsoaked.insomniac.com`) is read first and treated as a `promoter` source (also when an earlier run stored it as `discovered`); others are `discovered`. Confirming a lookup with such a page saves it as the series lineup URL, so the next lookup reads it directly. Aggregator pages can list other events' artists verbatim, so when two or more `discovered` pages were read, an act backed by only one of them is flagged for review (`merge.ts`). Brave is used when `BRAVE_SEARCH_API_KEY` is set and a Brave 429 parks the job until its reset; otherwise Gemini grounded search, which has no free-tier quota and is off in `wrangler.jsonc`.
5. **merge.** Claims are grouped by normalized name after applying learned aliases and the blocklist, then scored. Confidence is `1 - Π(1 - r)` over the source types listing the act, where `r` is each source's reliability (a prior, Clashfinder 0.93 above promoter 0.75 and archived pages 0.72, pulled toward its measured accept rate in your reviews). Each source that gave a full lineup for the edition (Clashfinder, promoter or archived page with 5+ acts) and leaves the act out scales it by `1 - 0.4·r` (`missingFrom`), so an act only a promoter page lists falls below the flag line when Clashfinder has the lineup, while a late addition only Clashfinder lists stays above it. Status becomes `needs_review`, or `no_data` if nothing was found.
6. **Review and confirm.** You accept, rename, reject (with a reason) or add acts, and tick who you saw; acts already marked as seen on the event start ticked. Confirmation writes the canonical edition (its facts default to the event's, with gaps filled from what the sources cited) and the learning data, links the event to the edition, and sets the event's seen acts to what you ticked plus any act you had added by hand that the lineup does not list (`mergeSeen` in `learning.ts`). It then queues MusicBrainz ID resolution. "Edit lineup" on a confirmed event reopens the review from the saved edition (`startRows` in `src/services/reviewRows.ts`: kept, renamed, cancelled and hand-added acts as you left them, rejected ones unticked); confirming again rewrites the edition and records corrections, but does not count source accuracy or read source pages a second time. Choosing another version of a confirmed lineup ("Not this version?", `replaceConfirmed`) runs a new lookup under the same edition key; the confirmed lineup stays until that lookup's review is saved. While it waits, the event page shows the lookup's progress card with "Review lineup" (`pendingReplacement` in `src/services/reviewRows.ts`), and the review starts in replace mode: the new version's acts start ticked (flagged ones unticked), keeping your saved spelling, role and set, with days and stages from the new source; acts only the old lineup had start unticked, except acts you added by hand. An act you split from one listing into B2B acts (Clashfinder's "Allen Watts + Talla 2XLC") keeps that listing's sources and set times on each act (`findWholeCandidate`: the listing must be exactly those names joined only by joiner words), and is not recorded as a rename or an added act. Reopening keeps the saved slot of each act, and an act you added that repeats one already listed with the same partners and set starts unticked. The review can be filtered by day and stage (`filterOptions`).

Job statuses: `queued`, `running`, `waiting_quota`, `needs_review`, `no_data`, `confirmed`, `failed` (after 3 errors with backoff).
