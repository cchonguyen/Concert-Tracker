# Quota and the queue

Part of [ARCHITECTURE.md](../../ARCHITECTURE.md).


- `QuotaLedger` (`src/server/lineup/quota.ts`) counts Gemini calls per model per Pacific day, against `GEMINI_DAILY_LIMIT` and `GEMINI_PER_MINUTE`. It refuses a call before it is made when the budget is spent.
- A Gemini 429 is parsed: a per-day quota parks the job until midnight Pacific; otherwise the job waits for the `retryDelay` Google returns (60 s if none).
- **Guarded reader.** Every model call goes through `GuardedReader` (`src/server/reader/guardedReader.ts`). The pipeline, the details route and discovery hold no provider client; `tests/readerGuarded.test.ts` fails if a file outside `src/server/reader/` and `src/server/lineup/gemini.ts` imports `@google/genai` or calls `.run(` on the AI binding. Provider is chosen by `READER_PROVIDER` (default `gemini`); there is no automatic fallback. Workers AI is a gated option that is not built yet.
- **MusicBrainz outages (`resolve_artists`).** A MusicBrainz 502, 503 or 504, a 429, or no answer (timeout, network) parks the job with `waiting_quota` and a retry time instead of failing it (`MusicBrainzUnavailableError` in `musicbrainz.ts`, parked in `runResolveArtists`). Backoff is 5 minutes after the first park, doubling for each consecutive park (10, 20, ...), capped at 6 hours; a 429 `Retry-After` is honored when longer. The count is read from the job log (parks since the last "Resolved" line), so there is no new column. Artists resolved before the outage stay saved. Nothing falls back to another source or to guessing, and the shared fetcher still spaces MusicBrainz calls. Other errors (a 404 or other 4xx) still use the normal 3-attempt retry and then fail. A MusicBrainz ID that another canonical artist already holds (`canonical_artists_mbid_key`, `ArtistIdTakenError`) does not stop the run: that artist is saved as checked without the ID, with a log line, and the run goes on. One-time repair: the owner-only `POST /api/manage/requeue-resolve-artists` (`requeueFailedResolveArtists`) puts `failed` `resolve_artists` jobs whose error mentions 503 back to waiting once; a log line marks each so none is re-queued twice. The Cron Trigger also runs it on the minute-0 run each hour (`isRequeueTime`), catching and logging any error.
- **Guards**, in order, before the call (`guard.ts`): 1 kill switch (`READER_ENABLED`), 2 breaker open, 3 unpinned model (`-latest`, only when the provider is set explicitly), 5 input size (`READER_MAX_INPUT_CHARS`), 6 calls per job (`READER_MAX_CALLS_PER_JOB`), 7 spend per Pacific day, 8 spend per UTC month, 9 calls per minute and per day (the `QuotaLedger` above). Guards 1, 2, 3, 7, 8 and 9 park the job with a retry time. Guard 5 returns `input_too_large` for that page only; guard 6 parks only its job; neither touches the breaker. A refusal makes no provider call and writes one `ai_calls` row with `outcome = blocked_by_guard` and a reason.
- **Circuit breaker.** Key `reader:breaker`. It opens after `READER_BREAKER_FAILURES` consecutive provider failures, on a provider 402 or 429, and on guards 7 to 9, for `READER_BREAKER_COOLDOWN_MIN` minutes (defaults 5 and 30). While open every call is refused as `breaker_open`.
- **Ledger keys** (`quota_ledger`, not `ai_calls`, so a missing log table can neither block nor unblock calls): `reader:spend:day:<YYYY-MM-DD>` and `reader:spend:month:<YYYY-MM>` in micro-dollars, `reader:calls:month:<YYYY-MM>`, `reader:job:<jobId>`, `reader:breaker`, plus the existing `provider:model:day`. The pre-call spend check is in memory (`used` plus the worst case for this call); one post-call write adds the real cost. If the ledger cannot be read or written the call fails closed (`guard_unavailable`). Defaults: $0.50 a day, $5 a month, 6 calls per job.
- **Call log.** One `ai_calls` row per call: when, feature, provider, model, outcome, guard reason or error code, token counts, cost. Never page text. A log write failure does not fail the read; it is counted. On the Supabase store the guards and the ledger and log writes run inside two database functions (`reader_preflight` before the call, `reader_settle` after it; migration 0040), so a guarded call costs 3 Worker subrequests instead of about 16. The functions make the same decisions in the same order with the same reasons; the per-minute window stays in Worker memory and is passed in. If the database cannot be reached, the call is parked as `guard_unavailable` (no provider fallback). The file store keeps the per-key logic in `src/server/reader/guard.ts`. Invalid JSON from the model drops that page with a log line, with no repair call and no retry.
- **Retention.** `deleteAiCallsBefore(cutoff)` exists on the store. Calling it from the cron is a follow-up; until then rows are kept.
- Parked jobs keep everything collected so far. Under Node, the worker (`LookupWorker` in `service.ts`) checks for due jobs every 20 seconds, one at a time. On Cloudflare a Cron Trigger sends due jobs to a Queue every minute and the queue consumer runs them one at a time (see Hosting). "Try now" in the UI retries immediately, past an earlier 429 pause but not past your own daily budget.
