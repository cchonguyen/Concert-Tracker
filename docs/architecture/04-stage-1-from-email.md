# Stage 1 from email

Part of [ARCHITECTURE.md](../../ARCHITECTURE.md).


Ticket confirmation emails are a stage 1 source for back-filling past shows. They propose events; you decide which ones you went to. Code: `src/server/events/email/` and `src/server/events/importRoutes.ts`.

1. **Feed.** Something with access to your mail posts raw messages to `POST /api/imports/email` (`{ emails: [{ id, link?, from, sentAt, subject, html?, text? }] }`, at most 100 per call, `Authorization: Bearer <IMPORT_TOKEN>`). Today that is Claude, reading Gmail through this project's connector and searching ticket senders. The feeder only copies messages; it interprets nothing. Without `IMPORT_TOKEN` the route answers 503.

   **Check email** feeds the same pipeline from the app itself, so you can catch up on new tickets whenever you like. You connect Gmail once ("Connect Gmail" in the review panel: Google sign-in, read-only `gmail.readonly` scope, `GET /api/gmail/connect` then `/api/gmail/callback` with a one-time state); the refresh token is kept in `app_settings` under `gmail`. "Check email" (`scanStep` in `email/scan.ts`) searches Gmail once per seller that has a reader (`sellerQuery`: `from:` its `domain`, plus the reader's `search` words for sellers whose domain also sends ads, such as Live Nation and TicketWeb) for mail received after the newest message that search already read, minus a day so late-arriving mail is not missed. A further search finds forwards (`forwardQuery`: a Fwd subject naming a seller's domain, not sent by you). Each search has its own cursor (`sellers` by domain, and `forwards`), so a newly added seller, or forwards, are searched through all your past mail once. A seller that already has rows on the review list when its cursor is first made starts from the shared watermark the earlier checks kept (top-level `scannedThrough`, now the furthest any search has read, for the page). The cursors, the time the last check finished, and the ids read within each cursor's day of lookback (so they are not read twice) are kept in `app_settings` under `email_scan`. Before the first check the watermark is the newest email already on the review list. Messages are read oldest first, four per request (the Workers CPU limit), and the page calls `POST /api/imports/scan` again until nothing remains; a check that stops halfway resumes where it left off. Gmail is searched once per check: the ids left to read are kept in `email_scan.queue`, so each later call only reads its four messages (Gmail limits how fast an app may ask); an unfinished check searches again after 30 minutes. Google's reason is shown with any Gmail error. When Gmail asks to slow down (429, or 403 `rateLimitExceeded`), the call answers 429 with `retry`, and the page waits 15 seconds and carries on, up to five times. A 403 for a missing permission asks you to connect Gmail again. A message Gmail will not hand over (404, or another 403) is skipped and counted, so it does not stop the check. Found shows land on the review list unticked, like any other import. Needs `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (a Google Cloud OAuth web client whose redirect URI is `<APP_URL>/api/gmail/callback`, published "In production" so the sign-in does not expire after 7 days) and migration `0006_app_settings.sql`. Without the keys the button is not shown. On the review list the server check sits under "More options" and only the owner sees it; members see the browser scan.

   **Browser scan** (`src/components/BrowserScan.tsx`, below Check email) runs the new engine, `@livearchive/ticket-scanner` (`packages/ticket-scanner`, a local `file:` dependency), in the page itself. It asks Google for a short-lived `gmail.readonly` token (Google Identity Services token model, `GOOGLE_CLIENT_ID` from `GET /api/imports/scan`; the OAuth client must list the site as an authorized JavaScript origin), runs `scanGmailInBrowser` over Stream A (seller senders) and Stream B (ticket words, `.pkpass`), and revokes the token when it ends. Mail bodies never reach the server: `POST /api/imports/proposals` takes `{ proposals, messages, updatedCursors? }` (only what was read, each value with its quote) and `mergeProposals` (`email/proposals.ts`) folds them into `email_imports` the way every import does: a value fills only an empty field, rows you added or skipped keep your choice, the same mail twice changes nothing. Its own two cursors live in `app_settings` under `email_scan_browser` and move only when "Check for new tickets" sends them. "Full re-scan (ignore watermark)" reads all past mail and never moves them. Every run saves what it finds straight into the review list; there is no dry-run option. The report shows: emails examined, proposals, by seller, unreadable (subject and link), skipped (no receipt wording), flagged, and net unique events (`summarizeScan`). `packages/ticket-scanner/tests/zeroCursor.test.ts` runs the whole synthetic corpus through this path from empty cursors against a fake Gmail (both streams, pages, `after:`) and checks it reads each message once, finds what `scanEmails` finds from the same mail, reports counts that add up, gives the same report on a full re-scan from saved cursors, and sends the token only to Gmail in the `Authorization` header.
2. **Read** (`readEmails`). Each message goes to the reader for its sender's domain (`EmailReader` in `email/types.ts`; one file per seller: Ticketmaster, Live Nation (its order card is Ticketmaster's, plus "View your mobile tickets" with "Mon, Oct 07 @ venue, City, ST"), Tixr, DICE, Resident Advisor, Eventbrite (including its 2013 and 2015–2018 layouts), AXS, Front Gate, TicketWeb (the confirmation's order summary and the tickets email's event details; reminders and event updates are not read)). The HTML is turned into the lines you see when you open the email (`htmlToLines`), and the reader copies the name, date, venue, city, order number, ticket count and total from fixed positions in the seller's layout, each value with the words it came from. No Gemini. Mail a reader does not recognise (ads, reminders) is ignored; a message whose subject announces tickets but whose body does not fit the layout is kept as `unreadable`, so you can open it and type it in. Once a newer reader reads that same message into a show, the unreadable row is no longer listed (`reviewList`). Add a seller by adding a reader with a test, never by loosening an existing one. A ticket a friend transferred to you (AXS "You Received Tickets") is read like an order. A ticket email someone forwarded to you (`email/forwarded.ts`) is read by the original seller's reader: the innermost forward header (Gmail's "---------- Forwarded message ---------" or iPhone Mail's "Begin forwarded message:") gives the original sender, subject and send day, and the lines below it are the original. The review row links to the forward you received. A forward whose header gives no readable send day is listed as unreadable, since a date written without a year is counted from that day. Sellers that name the ticket after the show ("DJ_Dave - Artist Presale", "2025 EDC Las Vegas - 3-Day GA Experience Pass") give the part before the last " - " when that part names a ticket type (`withoutTicketType`); the quote keeps the full line.
3. **Dates** (`email/dates.ts`). Sellers often leave out the year ("Sat Aug 29, 10:00 PM"). The year is then the only one, from two days before the email was sent to a year after, in which that day falls on the weekday given. No weekday and no year: no date, and the words are shown as written. A weekday that disagrees with a stated year means no date. A night that ends before noon the next day is one event on its first day.
4. **Group** (`mergeImports`). Messages about one show become one row (`EmailImport`), keyed by normalized name plus start date, else seller plus order number. A message whose order number is already on a row for the same date joins that row even under another name (a Front Gate receipt says "Second Show Added!", its tickets "(Saturday)"). A later message fills only empty fields. Refund, cancellation and transfer messages add a flag to the row with the same seller and name whose latest order came before them (a club night sold under one name every month gets only its own refund); one that arrives before its order is kept aside (status `flag`, never listed) until the order is read. A row whose date and name (equal, or one containing the other) match an event already in your log is linked to it and not offered again.
5. **Review** (`ImportReview`, opened from "N events found in your email" on the Events view). Rows are grouped by year and start unticked, because a ticket is not proof you went. Shows still ahead are listed apart; ticking one adds it as an upcoming event (planned, see Upcoming events and attendance), and unticked ones stay listed. "Add" turns the ticked rows into events (`POST /api/imports/add`); "Leave these out" marks them skipped (you did not go, or it was not a show at all) (`POST /api/imports/skip`, undoable).

   **Merge into an event you entered** (`mergeIntoEvent`, `POST /api/imports/merge`). When a row is a show you already typed in but the app did not match (a different name, no date yet), "Same as one of my events" on the row opens a picker of your events, nearest date first; a row already matched to your event offers "Merge into this event". Merging links the row to that event (status `added`) instead of making a new one, and follows the sync rule that newer edits are never overwritten: the email fills only the date, end date, venue, city and ticket price you left empty, each sourced as `email` with its link and quote. A field you filled stays as it is, and where the email says something different the review lists it as kept ("Kept yours: venue (the email says …)"). A start date is not filled when you gave a different year, the end date only alongside the email's own start date, and a price only where you never set or cleared one. Personal fields are untouched. The row records the fields it filled (`mergedFields`), so Undo (`POST /api/imports/unmerge`) clears just those, and only where the field still holds that email's value; anything you changed since stays, and the row goes back on the list.
6. **Save** (`eventFromImport`). The event gets the name, dates, venue and city from the row, each field sourced as `email` with the message link and the quoted words; details status `resolved` when dated, else `needs_date`. Personal fields (seen acts, rating, companions, notes) stay empty. The ticket price is the exception (R1.13): `ticketPriceOf` divides an email's dollar total (fees in) by the ticket count the same email gives, and the first email on a row that gives both sets the row's `ticketPrice`, quoted as "$40.00 for 2 tickets". The event takes it with an `email` source (`sources.ticketPrice`). `pricesFromImports` gives the same price to an event already in your log that a row is linked to, when it has no price and no `ticketPrice` source; a price you type or clear is marked `user` and never replaced. It runs on Add, on posted mail and on every Check email step. Check email also reads the order emails of rows that have no price once more, for the price only (`email_scan.prices` keeps the ids read until all have been). Counts come only from the email: Ticketmaster and Live Nation from one "Sec, Row, Seat 5 - 8" line, AXS from an order table with one ticket line, Front Gate from a receipt selling one item that is not a shuttle or parking.
