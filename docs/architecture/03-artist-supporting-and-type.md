# Artist, Supporting and type

Part of [ARCHITECTURE.md](../../ARCHITECTURE.md).


**Act names** (`src/server/lineup/actName.ts`). Edit lineup can keep a name whole (`oneAct`, stored on the edition performance): typing a name into a row with no B2B partners keeps it as one act unless the text has `b2b` or `vs` (" X " alone does not count, `hasUnambiguousB2bMark`). A kept-whole act is never split on blur, on save or on reopen, and a later lookup's "A X B" for the same name is not split either (`startRows` in `src/services/reviewRows.ts`). Before grouping, `mergeLineup` reads each claim's name with `readActName`: layout junk at the ends of a name (`[`, `]`, `*`, `_`, `|` and similar) is trimmed, never characters inside it; format and theme modifiers in parentheses (`(DJ Set)`, `(Live)`, `(Sunrise Set)`), presents connectors (`pres. HOLO`), and recognized Clashfinder delimiters are extracted into a clean artist name and a unified `set?: string` field while preserving the full quote. "A b2b B" (also "B2B", "back to back") becomes one claim per act, each keeping the whole quote, and the acts' candidates carry `b2b` (each other's keys); different sets by the same artist at the same festival become distinct performance slots. Confirming copies both onto ticked seen acts; a set modifier edited in review (`ReviewedPerformer.set`, `null` for none) replaces yours, otherwise `mergeSeen` keeps your earlier marks. Legacy `dj` and `live` values normalize seamlessly to "DJ Set" and "Live". The name shown is your most-used spelling of the same normalized name (`yourSpellings` over your seen acts), else the source's, put in Proper Case when it is all one case (`preferredSpelling`; one-word names of up to three capitals and DJ/MC stay as they are).

**Billing roles** (`src/server/lineup/billing.ts`). A role is read in code from a title a source wrote. `splitBill` finds the first marker (`with special guest(s)`, `special guest(s)`, `supported by`, `support from`, `w/`, `with`, `plus`); `billingFromTitle` gives the acts before it `headliner` and after it `support`, but only when a billed act is named on each side, so "An Evening with Bonobo" and "Fred again.. & Four Tet" give no role. The Ticketmaster adapter (`ticketmaster@2`) applies it to each listing's name and attractions and keeps the listing name as the claim's quote. `mergeLineup` keeps a role only when every claim that states one agrees. Review sends each act's role (`ReviewedPerformer.billing`, `null` for none); confirming stores it on the performance and on the seen act, with `roleFrom` `lineup` when it matches the sources and `you` otherwise. Clashfinder and setlist.fm give no roles; Gemini-read pages may (below). "Artist" is every seen act whose role is not `support` (`artistsOf` in `src/services/format.ts`); "Supporting" is the rest.

**From the event name** (`src/server/events/artists.ts`). `GET /api/events/:id` returns `suggestions`: acts named in the event's own name (whole words, after normalization) that a source lists for this event: the performers on the stage 1 candidate the event was matched to (Ticketmaster attractions, the setlist.fm artist; `DetailCandidate.performers`), the lookup's candidates, or the confirmed lineup. A marker in the name gives the role, by the same rule. The same list includes acts you saw at your other events whose name (4+ characters) appears in this one (`pastArtists`). `GET /api/events/:id/name-artists` adds parts of the name (`titleParts`: before a subtitle, without a year, split on billing markers, "b2b" and commas; "Above & Beyond" stays whole) that MusicBrainz knows as an artist of exactly that name with a score of 95 or more (`artistNamed`), at most 4 requests through the rate-limited fetcher. The event view offers each as one tap; nothing is added on its own.

**Roles from pages.** Gemini may return `billing` for a name (`extract@5`); it is kept only when `quoteBacksBilling` finds it in the quote: the nearest role word before the act ("Headliners:", "Support:", "special guest", "opener") names that role, or a marker puts the act on that side.

**Concert or festival** (`src/server/events/scale.ts`, shared with the browser). `eventScale(event, lineupFacts)`: your `kind` wins; otherwise festival when the end date is after the start date, more than 5 acts are known (confirmed lineup acts that were not cancelled, or seen acts), or the edition or the confirmed stage 1 date came from Clashfinder; concert when a confirmed lineup has 1 to 5 acts; otherwise not known. `GET /api/events` returns `editions` (per event: `{ acts, clashfinder }`, from `LineupStore.editionLineupFacts`) so the Table can work it out without loading each lineup. Only `kind` is stored, so the answer follows the event's dates and lineup.
