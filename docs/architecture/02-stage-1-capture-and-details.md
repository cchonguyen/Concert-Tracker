# Stage 1: capture and details

Part of [ARCHITECTURE.md](../../ARCHITECTURE.md).


1. **Parse** (`src/server/events/parse.ts`, shared with the browser for the live preview). The line is split in code: a date (`2024-10-05`, `10/5/24`, `Oct 5 2024`, `May 16-18, 2025`, `5 Oct 2024`, `October 2024`, or a bare year), explicit `weekend` tokens (`weekend N`, `wknd N`, `WN`, 1–9; preserving `"Vampire Weekend"` and literal `"W2"` in titles), then a place after ` at ` / `@` (venue, then city after a comma). ` in ` no longer marks a place on its own, so "Metallica in Concert" stays a name. Whatever is left is the name. The parse also keeps the full typed text (`text`) and lists up to two readings (`readings`: the split, and the whole line as the name, or a trailing ` in <City>` or comma reading) for research to try; each is taken from the typed words and nothing is invented. A year right after "the" is part of a name (The 1975), impossible dates are not dates, and nothing is filled in that you did not type.
2. **Save** (`POST /api/events`). The event is stored with what was parsed, each field sourced as `user`, details status `pending`. When the capture bar asks (`research: true`; list imports do not), the save also sends a `research` message on the existing `LOOKUP_QUEUE` (the message has a `type` field, a message without one is a lookup; no new binding) and returns `research: 'queued'` at once, so saving never waits on research. If the send fails the save stands, the event stays `pending` and the response says `research: 'pending'`. With no queue (the Node server) the browser asks for research itself, as in step 3. Saving from a canonical edition does not queue research.
3. **Research** (a queued `research` message, or `POST /api/events/:id/details` for "Look again", "Check details" and Fill gaps). The queue consumer (`runQueuedResearch` in `src/server/events/details.ts`) runs rungs 1 to 3 below (structured APIs and web search read in code) and never calls the reader model; rung 4 is Slices 11.16 and 11.17. It runs only while the event is still `pending`, so research that finished first is not overwritten, and it saves the result as candidates under the rules below. It reads and writes as the member who saved the event. An error is logged, the message is acked without retry and the event stays `pending` for "Look again". One message uses at most 13 subrequests: 2 store calls, 4 finders, 4 more if the typed name is searched too, and 3 place pages. The browser shows "Looking up details" and polls the event list every 3 seconds until the status leaves `pending` (it gives up after about 2 minutes). Without a year, only the finders that can search all years run (web search and setlist.fm, `withoutYear`); a web result must then also name the venue (or city) you gave, and whatever they find is offered as `choose`, never applied (nothing found: `needs_date`). If the event was renamed after saving and the current name finds nothing, the name parsed from what you first typed is searched once. Each configured finder in `src/server/events/details.ts` searches a window around what you gave (the date ±1 day, the month, or the year):
   - Ticketmaster: listings whose name has every word you typed; a festival listed per day is grouped by name and venue into one start and end date.
   - setlist.fm: shows by an artist of exactly that name on the date (or in the year), with venue and city.
   - Clashfinder: the edition matched in its event list (same rule as the lineup adapter), giving the start date.
   - Brave web search (`braveFinder`, when `BRAVE_SEARCH_API_KEY` is set): one query (`"<name>" <date or month or year> <venue> <city>`). A result counts only if its title and description name every word of the event; every full date written there (`findDates` in `parse.ts`) inside the window becomes a candidate whose source keeps the quoted words. These snippets only confirm stage 1 dates; they are never lineup evidence. Capped at 200 queries a month (`braveCapFetcher`); the backfill never uses it.
   - The reader model (today Gemini), only on Check details, then "Read with Gemini" (`{ useGemini: true }`; `geminiReader` in `src/server/events/detailsGemini.ts`, a `DetailReader`): the pages the other finders' web results came from plus the Brave results that name the event, never AXS. A page is sent to the reader model only if its text names every word of the event (and the year, when known); at most 3 pages, one call each, through the same `QuotaLedger` as stage 2. The reader returns the words the page uses for the date (`dateQuote`) and the place (`venue`, `city`, `country`, `placeQuote`; `details@1`). `checkedCandidate` keeps the page only if the date quote is on the page and `findDates` reads a date inside the window from it; a place value is kept only if it is in a place quote that is on the page (`isVerbatim`). The candidate's source has `readBy: 'gemini'` and both quotes. Out of quota (the ledger refuses or Google answers 429) it stops reading and notes it in `details.notes` (`gemini: ...`, shown on the event); nothing else reads in its place.
   - Rung 4 (built in Slice 11.17): after the rung 1 to 3 queue message, when the event has a full date and venue or city is still empty, the reader may run without a button press on at most 2 fetched pages, each under 30,000 characters (larger pages skipped, never cut up), one queue message per page (`research_reader`, taken from the pages rung 3 already found, no new search), inside the spend guards, and never during the save. A candidate fills empty fields only when its date is the full date you gave. A guard block or quota error parks it with a note: no retry, no other model. It follows the same `detailsGemini.ts` rules as above: quotes checked in code, results are candidates, nothing you typed is overwritten.
   Candidates on the same start date are merged, each field keeping the source that gave it. A failing finder is noted and the others still count. Sources write cities `City, ST` in the US and Canada (`cityLabel` in `src/server/events/place.ts`, from the region a source gives) and as the city elsewhere; an event stores the city and the state apart (see **City, state and country** below).
4. **Place from pages.** Search snippets give dates, not places. For the candidates that will be applied or shown, if a venue or city is missing, the pages that gave the date are fetched (at most 3 per research, never AXS) and their schema.org Event markup (`application/ld+json`) is read in code (`placeFromPage`): an event whose name or a performer has every word of yours, on a day the candidate covers, gives `location.name` as the venue and `addressLocality` plus `addressRegion` as the city. Several matching events at different places give nothing. The page is added as its own source for those fields, with the venue and city as the quote; it does not count as another date confirmation.
5. **Decide.** No candidates: `none`. If you gave a full date and one candidate covers it (or one covering candidate has more sources than any other): `matched`. The date is shown as confirmed with each source and quote, and the candidate fills only empty fields. Otherwise `choose`: up to 5 candidates wait for your pick (`POST /api/events/:id/details/pick`), which fills date and place from the candidate (the name stays yours), or for "None of these". Research never replaces a filled field; where the confirmed candidate differs from a saved field, the event view offers "Use … from <source>" under it, which takes just that field (`{ candidateId, fields }`).
6. **Edit** (`PATCH /api/events/:id`). Any field you change becomes a `user` source. `kind` (`concert`, `festival`, or `null` to go back to the rule) is your choice of type; seen acts may carry a `role` (`headliner` or `support`), kept as yours (`roleFrom: 'you'`) unless it is the lineup's role sent back. In the event view, "Last day" shows the start date until you change it (so the date picker opens on the right month) and is stored only when it differs; venue and city suggest what you have entered on other events (picking a venue you always gave the same city for fills an empty city), and city also suggests places from the Open-Meteo geocoding API as you type (`GET /api/places/cities`, `citySuggestions`). Suggestion fields (series, venue, city, and the Fill gaps editors) list their suggestions under the input while it has focus (`SuggestInput`, `suggestionsFor` in `src/services/format.ts`: the first eight when empty, else matches by `matchNames`) instead of a browser `<datalist>`, which phones barely show; a tap fills the input and saves it as if typed. Seen acts, companions, days attended, rating, ticket price and notes are edited the same way. Typing a seen act offers acts you entered on your other events (`pastArtistNames`, `matchNames` in `src/services/format.ts`: names starting with what you typed first, then names with a word starting with it, in the spelling you used most); Enter alone adds what you typed. Typing a companion does the same with people you entered on your other events (`pastCompanionNames`). Format is edited the same way, as chips: it can hold several values, stored in the one `format` text column separated by commas (`formatsOf`, `joinFormats` in `src/services/format.ts`), so the CSV and the sheet keep it in one column; typing offers formats from your other events, then a starting vocabulary. The Table's Format filter matches any one of an event's formats. "Days you went" sits under the dates. No days stored means you went every day: each day shows ticked, you untick the days you missed, the last ticked day cannot be unticked, and ticking every day again stores none. A seen act can carry `favourite` (a favourite set); `cleanSeen` preserves every favourite mark, and `mergeSeen` keeps them through a lineup review. A seen act can also carry `set` (unified performance format or theme modifier: `DJ Set`, `Live`, or custom strings like `Sunrise Set`, `Throwback Set`, `HOLO`, `Redux`; normalized from legacy `dj` and `live` for backward compatibility) and `b2b` (the keys of the other acts on this event it played B2B with), both yours only (`src/server/events/seen.ts`). Each performance instance carries an optional unique `id` (`randomUUID()`) to distinguish multiple sets by the same artist on one event (e.g. a solo set and a B2B set, or multiple distinct sets/themes). `cleanSeen` makes B2B links symmetric and joins chains into one group (`withB2b`), drops partners not on the event, and `mergeSeen` preserves each distinct performance through a review. An act in a B2B can also carry legacy `solo` and `soloSet`, which `seenSlots` unpacks as a distinct solo slot. Each act in a B2B stays its own seen act, so every count credits each artist; `seenSlots` and `slotLabel` group reciprocal partners for display ("A b2b B (DJ Set)"). In stats and metrics, each performance instance in `seen` counts as one viewing/set, while unique artist counts deduplicate by artist key. Every client patch of `seen` is built with `toSeenInput` so a change to one act never drops another's marks.

**Canonical edition (tapped suggestion & Option 3B fast-Enter).** As you type, the capture bar queries `GET /api/editions/suggest?q=` (debounced >=300ms), matching across edition `name`, attached series `name`, `brand`, and `aliases`; each shows its date or year, draft editions are excluded, and multi-weekend editions remain offered for re-selection. A tap saves with `POST /api/events { text, editionId, weekend? }`. `newEventFromEdition` (`src/server/events/service.ts`) starts from the same parse as `newEvent`, then copies only the edition's known name, attached canonical `series`, year, venue, city, `region`, country, and dates (populating Weekend N's dates when a weekend was typed/picked, or leaving dates empty on multi-weekend editions until the Event Detail `"Which weekend did you go?"` soft-prompt—with `"Other dates"` escape hatch—is answered), each sourced `{ sourceType: 'edition', editionId }`. A missing fact stays missing, and personal overrides stay local to `logged_events` without mutating `event_series` or `event_editions`. On pressing Enter without picking a dropdown suggestion (**Option 3B**), a pure normalized matcher checks verified series editions: if **exactly 1** matches unambiguously (title/series match, date within edition dates or `weekends`, venue/city matching or empty, no conflicts), it auto-links immediately; if **2 or more** match (e.g. W1 vs W2 or multi-city), it does not auto-link and instead surfaces 1-tap canonical disambiguation candidates with a `"None of these — search web / keep mine"` escape hatch; 0 matches proceed with normal Stage 1 capture. Linked editions set `details.status = 'matched'`, skip Stage 1 research, and start the lineup lookup at once with zero network calls; nothing personal (`seen`, companions, rating, price, notes, format, type) is copied. An unknown or draft edition gives 404 and saves nothing.

**Provisional editions and inheritance (planned, approved 2026-11-13; Slices 11.8 to 11.22, not built).** A member's own entry may create a `provisional` shared edition with name, date, venue and city only, never personal fields; the member notice version goes up and members accept it again before phase 2 ships. A ticket email import that became an event is a `verified` source for those four fields. A linked event will show the edition's value unless the person overrode that field; the first-typed values are kept as `captured` and never deleted. Every change to a shared edition is recorded (old, new, who or what, why) and can be undone. Shared tables, traces, logs and the review queue never hold companions, notes, rating, price or attendance. Details: `docs/ingest-canon-plan.md`.

**Series** (`LoggedEvent.series`, migration `0009_event_series.sql`). Your name for the festival or tour an event is one edition of, set through `PATCH /api/events/:id` (`series`, `null` clears it). `eventTitle` in `src/services/series.ts` shows an event in a series as "<series> <year>" everywhere the app names it, adding the town of the event's stored city (`townOf`, the part before the comma) when the series name does not already contain it (`withPlace`); `name` is unchanged and is still what stage 2 reads, so the canonical `event_series` is not affected. The Series panel (`SeriesPanel`, in the Manage tab's Series list; the Table's Series button opens it there) offers groups from `seriesSuggestions`: events whose names are equal once `seriesBase` takes out the year (`2024`, `'24`, not a year right after "the"), and a weekend, day or night number, and whose city has the same town, that are not all in one series yet. An event with no city is grouped with the one town its name is known in, if there is exactly one; otherwise it is left out. The name offered is a series you already use for that key, else your most used spelling with the town added (`withPlace`), so one festival in two cities becomes two series. Linking saves each ticked event through the event route, one request per event. The panel also renames a series for all its events (in Manage, through the series record's rename), adds another event to it, or takes one out; the event view has a Series field with your series and the name's base as suggestions. `LoggedEvent.weekend` (1 to 9, `PATCH` `weekend`, `null` clears it; migration `0011_event_weekend.sql`) is the weekend of a festival that runs more than one; `eventTitle` appends " · Weekend N". It is picked on the event or per row in the Series panel, where the default is what `weekendFromName` reads from your own name for the event ("Weekend 2", "Wknd 2", "W2"), saved only when you link. A `Weekend` CSV column is read back on import. An event's series tag in the Table filters to that series in one tap.

**Artist in the title.** Outside a series, `eventTitle` puts the event's main acts first when there are one or two of them (`artistsOf`: seen acts not billed as support) and `eventScale` does not make it a festival: "<act>, <act> - <name>", or "<act> b2b <act> - <name>" when the two are marked B2B. Views render it with `EventTitle` (`src/components/EventTitle.tsx`, from `eventTitleParts`): the acts at the usual weight, the event's name after them a little softer. The name is shown as typed when it already contains one of those acts (compared with `seriesKey`). `name` never changes; the event view shows the title under "Shows as" when it differs.

**Set times.** `mergeLineup` keeps one `CandidateSource` per page and act, with every set that page times for it (`sets`: day, stage, start, end; Clashfinder gives them). They are stored inside `performances.sources`, so they stay cited and need no column. The event view shows each seen act's stage and time (`actSets`, `setLabel` in `src/server/events/sets.ts`), narrowed to the days you went when you gave them. Each lineup chip shows its first set's day (multi-day events) and start time (`chipTime`), and a lineup with any timed act is ordered by earliest start after the day and stage filters, untimed acts after (`byStartTime`). Lineups confirmed before this have no set times until they are looked up again.

**City, state and country.** An event stores `city` ("Las Vegas"), `region` (the state or province: the postal code in the US and Canada, in full elsewhere) and `country`, each with its own source. `splitCity` / `splitEventCity` in `src/server/events/regions.ts` (shared with the browser) split a city written with a US or Canadian postal code ("Las Vegas, NV", "Austin, TX, USA") into city and state, and fill the country that code belongs to when none is stored; the split part keeps the city's source. Nothing else after a comma is touched. It runs on capture, on every edit of the city (where the state you just typed replaces the stored one), when a source's city is taken, and in both stores on read and write, so rows saved before the State column (migration 0010, which splits them the same way) read back split. A US or Canadian state you type fills an empty country the same way. `cityWithRegion` writes "Las Vegas, NV" back for display, the Table's city filter and sort, the Map, Stats and Artists counts, weather, and the lineup and research queries. Anything a postal code can't settle is looked up only on request: `GET /api/places/guess` (`placeGuess` in `place.ts`) asks the Open-Meteo geocoder for populated places by that name that fit any state or country you wrote, groups them by state and country, and gives one when there is a single group or the biggest is at least ten times the next (Las Vegas, NV over Las Vegas, NM); otherwise a note says why. The event view offers it under State and Fill gaps ("State & country") for many rows with "Use" and "Use all"; `placePatch` (`src/services/table.ts`) fills only the missing parts, so nothing you typed is replaced.

**Weather** (`src/server/events/weather.ts`). Only when you ask (`POST /api/events/:id/weather`, or "Weather" in Fill gaps), and once, server-side, when `POST /api/events` saves an event from a canonical edition (after the lineup link; never re-run, and a failure never fails the save). It needs a start date at least 5 days past and a city. The city is placed with the Open-Meteo geocoder only when exactly one populated place matches it (`placesFor`: the "City, ST" or "City, Country" label, or a bare name shared by no other place). It is tried as written first, then in its common spellings from `cityVariants`: a trailing " City" dropped ("New York City, NY" becomes "New York, NY"), "NYC" read as "New York", and a full state name after the comma written as its postal code ("Austin, Texas" becomes "Austin, TX"). The first spelling that matches one place is used; a spelling that matches several stops the search and says it is ambiguous. If none matches, it says why and stores nothing. The Open-Meteo archive then gives each day's high, low, rain and WMO code (up to 14 days), stored as `LoggedEvent.weather` with the place, coordinates and the archive URL.

**Upcoming events and attendance** (`src/server/events/attendance.ts`, shared with the browser; `LoggedEvent.attendance`, migration `0012_event_attendance.sql`). An event can be added before it happens. `newEvent`, `eventFromImport` (a ticked email show still ahead) and `applyPatch` (when an edit or a list import sets dates that are all after today, `isAhead`) store `attendance: 'planned'`; nothing else sets it. You answer in the event view (`WentCard`): `PATCH` `attendance: null` means you went, `'missed'` that you didn't, and `'planned'` puts it back. A stored `'missed'` survives date edits. `attendanceOf(event, today)` works out the state each time: `went` (no value, and not dated ahead, so rows saved before planning existed still wait while ahead), `upcoming` (planned, last day after today, `lastDay` reading a month or year as its last day), `confirm` (planned, last day today or earlier, or no date left) and `missed`. Only `went` events count: `wentTo` filters what the Stats view (`pastEvents`), the Ranking view, the Map, the header's artist count, the home tiles (`homeSummary`) and the Table's summary (`summarize`) see, and Fill gaps does not ask for who you saw, a favourite or a rating on the others. The home lists `confirm` events under "Did you go?" and counts them in its needs chips; the Table shows a badge for every state but `went` in its Details column (not beside the title) and filters on it (`went=` in the address); Stats says how many are waiting. In `WentCard`, "Yes" saves `attendance: null` at once and then offers the event's seen acts (ticked) and the confirmed lineup's acts (unticked) as one-tap chips, the days you went for a multi-day event (`DaysWent`), and "Review the lineup" when one is waiting; nothing is ticked that was not already on the event. The CSV and the sheet carry a worked-out `Went` column (Yes, Upcoming, Not confirmed, No) that is not read back, so sync never changes attendance. Migration 0012 marks rows already saved with a date ahead as planned.
