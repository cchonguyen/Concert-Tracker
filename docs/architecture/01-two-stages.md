# Two stages

Part of [ARCHITECTURE.md](../../ARCHITECTURE.md).


| | Stage 1: the event | Stage 2: the lineup |
| --- | --- | --- |
| Started by | Typing a line and pressing Add, or ticking shows found in your ticket emails | "Find who played" on a saved event |
| Code | `src/server/events/` | `src/server/lineup/` |
| Sources | Ticketmaster, setlist.fm, Clashfinder, Brave web search and the event markup on the pages it found, your ticket emails (all read in code) | Clashfinder, promoter pages, Ticketmaster, setlist.fm, web search |
| Gemini | Only on Check details, then "Deep search with AI": reads up to 3 found pages | Reads fetched pages |
| Runs | Inside the request, a few seconds | A background job (queue), can wait for quota |
| Stores | `logged_events` (your log) | Canonical edition, evidence, learning data; links the event to the edition |

Stage 2 never changes the event's date or place, and stage 1 never waits on stage 2.

The owner can also start a canonical lookup for an edition with no saved event ("Ingest canonical lineup", owner only). It writes only to the shared catalog (`event_editions`, `performances`, `canonical_artists`) and never to any member's `logged_events`. Such a lookup follows the same quota, fetch and verbatim rules as stage 2. Only confirmed editions feed member suggestions; drafts stay with the owner. The owner starts a canonical lookup with no event through `POST /api/manage/canonical/ingest` (owner only; the job has no `eventId`). The archive's Lookups section (`CanonicalArchive.tsx`, `ArchiveLookups`) shows those jobs from `GET /api/manage/canonical/lookups` (owner only, newest first, `eventId` absent) with status in words (queued, fetching, waiting for quota, ready to review, no lineup found, saved, failed) and the error for a failed one. Review opens the review in canonical mode; Retry runs the job again (`POST /api/lookups/:id/run`). A submit shows the new job at once, and a failed submit shows its error in the form. The list checks again every 20 seconds while a job is queued, running or waiting for quota. The older `POST /api/lookups` also needs the owner now; members start lookups through a saved event (`POST /api/events/:id/lineup`). The owner confirms an edition with `POST /api/manage/canonical/confirm` (previews the merge diff unless `apply: true`; stored acts are kept, blank facts filled, differing facts reported and not overwritten). A save from Review sends the lookup's `jobId`; a successful save marks that catalog lookup `confirmed` with its edition, so its line leaves "Review" in the Lookups list. A personal lookup (one with an `eventId`) is never changed by this route. The owner sees a Global Archive scope in Manage (owner only; the scope switch `My records | Global archive` sits above the section menu in `ManageView.tsx`, and it changes what the menu, search and filters act on). Its menu has three sections only: Artists, Editions & Lineups and Lookups. Venues, Places, People, Series, Organizations, Labels, Data health and History are hidden in archive scope, not shown inert. The search box filters the active section (artists by name or AKA, editions by name, series or venue), the edition status filter shows only on Editions, and Lookups has no search. Each section body is rendered by `ManageView` through `CanonicalArchive` (`src/components/CanonicalArchive.tsx`: `ArchiveArtists`, `ArchiveEditions`, `ArchiveLookups`); there is no stacked panel layout. Lookups holds the ingest form and the lookups list. Artists show the catalog as records: each row has the name, its AKAs, origin badges, whether it has a MusicBrainz ID, billed editions and community count, and its detail (`CanonicalArtistEntry.tsx`, the sibling of `ManageEntry.tsx`) adds rename, merge, AKA add and remove, and the appearances; edits are described in the catalog artists paragraph below. Editions show the catalog list as it is now. Nothing is invented: a list shows only what the catalog holds, and missing data says so ("No MusicBrainz id yet", "Community count not available"). The community count per artist is the number of members with that name on a live event: `canonical_community_counts()` (migration 0033, service role only) returns a name key and a count, never a member or an event. Members never see the archive. Admin-curated acts use the `user` source type with extractor `admin_curation` and an optional weblink.

**Subrequest budget** (`src/server/lineup/budget.ts`). Workers count every external fetch and every Supabase call against one invocation, and the limit is 50. Each invocation has its own budget, started in three places: each `/api` HTTP request (an Express middleware mounted first on `/api`), each queue message (one stage or one page of extraction, `worker/index.ts`), and each cron run. The limit is 50, or `SUBREQUEST_LIMIT` when that is a positive whole number. Ordinary calls stop at the limit minus a reserve of 4, so the last 4 stay free for the job's final save (`runJob`) and the queue's error-path saves, which take from the reserve. A call past that point throws `BudgetExhausted`. An edition's change record, written by `writeEdition` right after the edition is saved, also takes from the reserve (`runReserved`), so a spent budget cannot leave a saved change without its history row. Outside any budget nothing is counted. The rate-limited fetcher (`http.ts`) charges one per attempt and one per redirect hop: redirects are followed by hand, at most 3 hops, each checked as a public address. Bodies are read up to `maxBytes` (3 MB by default); a longer body is cut and marked `truncated`, and a declared `content-length` over the cap is refused without reading it. Supabase clients pass `countingFetch`, so their calls are counted.
