# Rules for anyone changing this app

Read [REQUIREMENTS.md](REQUIREMENTS.md) first: it says what the app is for (remembering which events you went to and who you saw) and ranks the principles that settle trade-offs. Read [ARCHITECTURE.md](ARCHITECTURE.md) before changing capture, lineup lookup, storage or review. These rules apply to people and AI coding agents alike (Claude, Gemini in AI Studio, Copilot, and others). If a change conflicts with them, change REQUIREMENTS.md or ARCHITECTURE.md first and say why.

- Never make up or default a lineup, date, venue, stage, rating or setlist, and never let a model answer from memory. An inferred value (approved 2026-11-24, `docs/specs/inferred-values.md`) is allowed only as that spec says: a stated reason with named inputs, the "Inferred" label, never over a typed or verified value, never counted toward verifying anything. Until a slice of that spec changes a rule below, the rule stands. Missing data with nothing to go on stays missing and the UI says so.
- Every stored act must reference a stored source document and a quoted span from it.
- The reader model (Gemini today) may only extract from text the app fetched. It never answers from memory and is never asked for confidence, dates it was not shown, or URLs. In "Deep search with AI" it may also return a venue, city, state or country it infers from such a page, with an exact quote from the page and a one-line reason; code checks the quote is on the page and stores it only as an inferred value on the shared edition (`docs/specs/inferred-values.md`). It never infers a date.
- Reject any extracted name that is not found verbatim (after normalization) in its source text. Do not loosen `isVerbatim`.
- A billing role (headliner or support) is stored only with a quote that contains the marker words ("with special guest", "supported by", ...) and a billed act on each side (`src/server/lineup/billing.ts`). List order, font size or position never make a headliner. The one exception is an inferred role, never a stored one: a concert named after exactly one of its listed acts, with no stated role on the lineup, shows that act as an inferred Headliner and the others as inferred Support (`src/server/canon/inferredBilling.ts`, `docs/specs/inferred-values.md`). No role means "Artist".
- Concert or Festival is worked out in code (`src/server/events/scale.ts`); store only the person's own choice.
- Format is the person's own words; the app suggests past values but never fills it.
- Suggestions from an event's name (a source's listing, your other events, MusicBrainz) are one-tap offers; nothing is added to seen acts without a tap.
- Set times come only from a source that times them, stored on that source. A set-times page the owner pastes with its link (approved 2026-11-24, `docs/specs/pasted-set-times.md`) is such a source: it is stored as a `pasted` source document, read in code only (`src/server/lineup/pasted.ts`), and the app never fetches its link. Weather is looked up only when asked, or once per canonical edition when a member saves an event from it, only for a city that matches exactly one place, and stored with its URL. The edition's record is shared and refreshed only by an admin request, and each change is logged. A month-only event gets no weather.
- Confidence is computed in code from sources and review history.
- Every model call in the app goes through the guarded reader (`src/server/reader/`): spend guards and the circuit breaker run first, one `ai_calls` row is written after, no page text goes in it, and there is no automatic switch between providers.
- On a quota error (any provider), park the job and stop. Do not retry with another model and do not fall back to heuristics or regex parsing.
- Do not add hardcoded lists of festivals, venues or artists. Improve an adapter or add a new one under `src/server/lineup/adapters/`.
- Respect source limits through the shared rate-limited fetcher (MusicBrainz 1 request/second). Do not scrape AXS.
- Keep the canonical lineup and the personal event log (`logged_events`) separate.
- Shared-edition rules (approved 2026-11-13, built in Slices 11.8 to 11.23):
  - A member's own entry may create a `provisional` shared edition (name, date, venue, city and state only; never personal fields). Built in Slice 11.23; the state was added 2026-11-24, the member notice version is now 4 (2026-11-26: act names in the owner's genres file), and members accept it again.
  - A ticket email import that became an event is a `verified` source for an edition's name, date, venue, city and state (the state is split from "City, ST" in code).
  - A linked event shows the edition's value unless the person overrode that field; what they first typed is kept as `captured` and never deleted.
  - Every change to a shared edition is recorded (old value, new value, who or what, why) and can be undone.
  - Shared tables, traces, logs and the review queue never hold personal fields (companions, notes, rating, price, attendance).
- Auto-verify (approved 2026-11-18, `docs/auto-verify-spec.md`):
  - An act is `verified` when a usable source has its name and date for the same edition: a ticket email, a promoter or lineup page the app fetched and stored, a set-times page the owner pasted with its link, or an API record. One trusted source is enough. Two distinct fetched sources that agree also verify it. Setlist.fm IDs alone never verify an act.
  - A member's own tick enters as a `candidate` with source `your entry` (the typed text as the quoted span). A single member's ticks never verify an act. Two different members ticking the same act on the same shared edition do (approved 2026-11-27, `docs/specs/series-sync.md` Rule 1c): the hourly run counts them in memory only (who ticked what is never stored) and lifts the candidate to verified (`src/server/canon/memberTick.ts`, actor `system:member-verify`, logged and undoable; an undone one is not redone). The other exception is an inferred value (`docs/specs/inferred-values.md`): a member's Verify tap lifts it to Candidate, and when two different members verify the same one it is written to the shared edition as verified (`src/server/canon/inferenceReview.ts`, actor `system:member-verify`, undoable); the owner's Confirm does the same at once.
  - An edition becomes `verified` in code only when its name, act, location, venue and date all have values from verified sources. A value the owner typed is never overwritten, and no status is demoted automatically.
  - Venue fill (approved 2026-11-24, `docs/specs/venue-location-fill.md`): a known venue fills only an edition's or event's empty city, state and country, from one place on the shared venue records (several places are offered as choices, and when one place holds a majority of at least 2 of the venue's shared editions it is also stored as an inferred value, never in the edition's own fields: `docs/specs/inferred-values.md`) or from its own "City, ST" text. A location written by the venue fill counts as a location from a verified source; an inferred one never does.
  - Every automatic change goes through `writeEdition` with a system actor and a reason, is recorded in `edition_changes`, and can be undone.
- Artist genres are shared: one set per artist, the same for everyone (approved 2026-11-26, `docs/specs/canonical-genres.md`). They come only from the music-story export, MusicBrainz read through music-story's genre map when asked, or the owner (`src/server/events/genres.ts`); the owner's win and are labelled as set by the owner. Only the owner changes them. Every change goes through `writeArtistGenres`, is recorded in `artist_genre_changes` (old value, new value, who or what, why) and can be undone. A member may add genres of their own to an act (`user_artist_genres`): added on top of the shared ones, never hiding or replacing them, shown only on that member's screens and never in shared tables, the export or the log. Never infer a genre from a name, an event or a model; an act with none stays without one. Genre spellings that differ only in capitals, accents, spaces, hyphens or punctuation are one genre (`genreKey`, `src/server/events/genreVocabulary.ts`); code never joins different words, stems or drops words. The owner's genre vocabulary (shown spelling, group, aliases, merges, umbrella genres) is shared, holds no personal fields, is changed only by the owner through `writeGenreVocabulary`, is recorded in `genre_changes` and can be undone. Stored genres are resolved through it when read, never rewritten by it, and an umbrella never adds a genre to an act. Genre taxonomy (approved 2026-11-27, `docs/specs/genre-taxonomy-phase-a.md`): the owner's vocabulary puts each genre under one scene family and each family under one macro genre. These replace music-story's groups as the top level. A total by family or macro resolves a stored style through its alias to the genre's `primary_parent_key` when it is read, never through a stored `parent`. The owner's own genres are ranked: their order sets their weights (1.0, 0.70, 0.45, 0.25, then 0.25), and music-story and MusicBrainz weights stay as sent. Secondary families, adjacent genres and derived-from links live in `genre_relations`, never add to a total, change only through `writeGenreVocabulary`, are recorded in `genre_changes` and can be undone. Rows with origin `curated` are the owner's. A logged, undoable system job may write `artist_cooccur` and `lineup_cooccur` rows computed only from shared tables (`artist_genres`, `performances`), never over a `curated` row. No relation is computed from any member's events, attendance or companions. Artist orbits (`artist_orbits`, `artist_orbit_members`; approved 2026-11-27, `docs/specs/genre-taxonomy-release-3.md`) are the owner's shared curation: changed only by the owner through `writeArtistOrbits`, recorded in `artist_orbit_changes` and undoable, never counted in a total; a member is sent the orbits that include an act from their own events or records, with each orbit's roster by name.
- The owner's genres file lists every act any member marked as seen, once by name, read only through the `seen_act_names()` database function: no member, event, date or count. A member is sent genre rows only for acts in their own events or records.
- Ticket emails are read by per-seller code under `src/server/events/email/`, never by Gemini. An imported show becomes an event only when you tick it, or is merged into an event you entered only when you pick that event (filling only its empty fields, undoable), and never fills personal fields, except a ticket price worked out from the same email's dollar total and ticket count, and only where the event has no price you set or cleared.
- Capture is two stages. Saving an event (stage 1) never waits on research, quota or a lineup; the lineup lookup (stage 2) only starts when asked for on a saved event.
- Stage 1 research uses structured APIs and web search results read in code. The reader model runs in stage 1 when you press "Deep search with AI" in Check details on an event, and (approved 2026-11-13, built in Slices 11.15 to 11.17) without a button press only as rung 4 of the research ladder: at most 2 pages, each under 30,000 characters, inside the spend guards, in its own queue message after the save. It reads only pages the app fetched, and its dates are read in code from the quote it gives (`src/server/events/detailsGemini.ts`). Never call it during saving, from plain "Look again" or from Fill gaps. Its results are candidates: they never overwrite a field you typed, and fill empty fields on their own only when they match the full date you gave.
- Parse the capture line in code (`src/server/events/parse.ts`); text it cannot place stays in the name. Never add a model call to parsing.
- Keep capture to one line of text. New personal fields go on the event detail, not on capture.
- No demo or seeded data in the app. An empty app is empty. The one exception is sample mode: the app's own views over fictional sample data (`src/demo/sampleData.ts`), used at `/demo` and by a signed-in account that is not invited. Sample mode turns on only at start-up (`src/services/sampleMode.ts`), never on a network error; the sample is loaded by a dynamic import only in that mode, is never mixed with real data, is never sent to the server or written to the database, and every sample page says it is sample data.
- Public pages at the base address (`/`, `/privacy`, `/terms`, and any new page there) are listed in `PUBLIC_EXACT_PATHS` in `src/server/site/publicPaths.ts` in the same change that adds them. The Worker refuses every page not on that list once Access is on, and `tests/publicPagesList.test.ts` fails when one is missing. Anything under `/app` or `/api` stays off the list.
- Run `npm run lint` and `npm test` before committing, and add tests for new adapters or rules.
- Update ARCHITECTURE.md (and REQUIREMENTS.md, if a requirement changes) in the same change when behavior described there changes.
- When designing a new subsystem or modifying more than 3 architectural areas, present the plan and file breakdown first, and wait for confirmation before modifying code.
- Store multi-step feature plans and design specs inside the repository (under `docs/` or `specs/`) rather than only in ephemeral session artifacts.

## Design system

- Shared UI components live in `src/components/ui/` (IconButton, BackToTop, MenuButton, Popover, Pill, and the landing look's PosterHeading, PostIt, AppBackdrop and Logo). Use them for new UI.
- The landing look is the app's standard (`docs/specs/landing-look.md`): titles use `PosterHeading`, callouts use `PostIt`, the second colour comes from `--la-second` (Tailwind `text-second`), and every new style lives in a design-system module under `src/styles/`. The catalogue is `docs/design-system/design-system.json`; update it in the same change.
- The design-system approach is wanted: when you touch a component that has its own inline copy of one of these patterns (a dropdown, a tooltip, an icon-only button, a pill, a back-to-top), move it onto the shared component in the same change. Do not build a fresh copy.
- Only add a shared component when the current change needs it. Do not build the whole library ahead of use.

## Harness Sector 000 Card Catalog (Falcon Protocol)

You are **THE FALCON (`fa`)**, the main session. Coordinate the work and hand slice-sized edits to subagents. The full rules are in `.claude/harness-rules.md` (Claude Code also loads `CLAUDE.md`); this block keeps only what an agent that reads nothing else needs.

### 1. Dispatch
- An `[IN_PROGRESS]` slice in `.spec/PROGRESS.md` with known `Target files:`: dispatch `gf-coder`.
- Requirements unclear, `Target files:` unknown, or `.spec/BLACK_BOX.md` exists: dispatch `el-architect`.
- Fast-path budget for the main session (`fa_fast_path` in `.harness/config/thresholds.json`): 3 source reads, 1 search, 1 single-file edit of at most 25 lines. Delegate before you go over; the hooks only warn.
- Antigravity: subagent payloads for `define_subagent` are in `.harness/agents/runtime-payloads.json`.

### 2. Slices and checks
- Start a slice with `node .harness/scripts/start-slice.mjs` and finish it with `node .harness/scripts/finish-slice.mjs "<msg>"`, which marks it `[x]` and stamps the Referee trailers.
- Run the project's typecheck, lint and test commands (see `CLAUDE.md`, Project-Specific Commands) once after the final edit.
- Open only the Atlas coordinates a slice's `Coords:` names (`.spec/ATLAS.md`).

### 3. Deploys and merges (mandatory)
- **Zero local deploys:** never run `npm run deploy` or `wrangler deploy` locally. Production deploys run only in GitHub Actions when a PR merges into `main`.
- **Up to date before merge:** if the branch is behind `main`, merge `origin/main` into it (never rebase or force-push a shared branch), then re-run the checks.
- **Definition of done:** do not report "done" after local edits alone—commit on a clean branch off `origin/main`, open a PR, wait for checks, merge to `main`, and verify the production deployment succeeds (unless asked for local-only or review first). Keep harness syncs separate from feature PRs.
