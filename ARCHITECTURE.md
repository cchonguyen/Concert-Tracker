# LiveArchive architecture

This is the source of truth for how LiveArchive captures events, finds lineups and stores what you have seen. Anyone changing the app, person or AI agent, should read it first and keep it current. What the app is for, and the principles behind it, are in [REQUIREMENTS.md](REQUIREMENTS.md); the rules an agent must follow are summarized in [AGENTS.md](AGENTS.md).

## Goal

You type one line about an event you went to. It is saved at once (stage 1), and the app looks up its date and place from structured sources, suggesting rather than overwriting. Later, whenever you like, you ask it to find who played (stage 2): it finds the lineup with a citation for every act, lets you confirm it and tick who you saw, and stores the result so the same edition never has to be looked up again. When an API has no capacity, the lookup waits in a queue. It never guesses.

## Two stages

| | Stage 1: the event | Stage 2: the lineup |
| --- | --- | --- |
| Started by | Typing a line and pressing Add, or ticking shows found in your ticket emails | "Find who played" on a saved event |
| Code | `src/server/events/` | `src/server/lineup/` |
| Sources | Ticketmaster, setlist.fm, Clashfinder, Brave web search and the event markup on the pages it found, your ticket emails (all read in code) | Clashfinder, promoter pages, Ticketmaster, setlist.fm, web search |
| Gemini | Only on "Look again with Gemini": reads up to 3 found pages | Reads fetched pages |
| Runs | Inside the request, a few seconds | A background job (queue), can wait for quota |
| Stores | `logged_events` (your log) | Canonical edition, evidence, learning data; links the event to the edition |

Stage 2 never changes the event's date or place, and stage 1 never waits on stage 2.

## Invariants

These are enforced in code. A change that breaks one is a bug, even if the output looks more complete.

1. **No claim without evidence.** Every act in a lineup carries at least one source URL and the text it was found in (`PerformerClaim.quotedSpan`). Facts (dates, venue) carry their source too.
2. **Gemini is a reader, never a memory.** Gemini only extracts names from text the app fetched and stored. A name is kept only if its quoted span occurs in the stored page and the name occurs in the span (`isVerbatim` in `src/server/lineup/text.ts`).
3. **Confidence is computed, never asked for.** It comes from which sources agree and how often each source has been right in your reviews (`src/server/lineup/merge.ts`). No model is asked for a confidence score, a URL it did not find, or a date it was not shown.
4. **Empty is a valid answer.** If no source lists a lineup, the lookup ends as `no_data` and you enter acts by hand. There are no default dates, cities, venues, stages, ratings or setlists anywhere.
5. **Resolve once, reuse forever.** An edition (series plus date, or year when the date is unknown) is confirmed once; later lookups read it from the database with zero network calls.
6. **Quota is a resource, not an error path.** The app tracks its own Gemini budget and parks a job with a retry time when capacity runs out. There is no fallback model cascade and no heuristic substitute.
7. **The lineup is a fact about the world; what you saw is a fact about you.** Canonical editions and your event log are stored separately. "Artists" counts only acts you marked as seen.
8. **No hardcoded knowledge.** No lists of festivals, venues or artists in code. Fix a data source or add an adapter instead.
9. **Your word wins.** Stage 1 suggestions never overwrite a field you typed. Every event field records its source (`LoggedEvent.sources`): you, or a source URL.

## Stage 1: capture and details

1. **Parse** (`src/server/events/parse.ts`, shared with the browser for the live preview). The line is split in code: a date (`2024-10-05`, `10/5/24`, `Oct 5 2024`, `May 16-18, 2025`, `5 Oct 2024`, `October 2024`, or a bare year), then a place after ` at ` / `@` (venue, then city after a comma or ` in `) or after ` in ` (city). Whatever is left is the name. A year right after "the" is part of a name (The 1975), impossible dates are not dates, and nothing is filled in that you did not type.
2. **Save** (`POST /api/events`). The event is stored with what was parsed, each field sourced as `user`, details status `pending`.
3. **Research** (`POST /api/events/:id/details`, called by the browser right after saving; also "Look again"). Without a year, only the finders that can search all years run (web search and setlist.fm, `withoutYear`); a web result must then also name the venue (or city) you gave, and whatever they find is offered as `choose`, never applied (nothing found: `needs_date`). If the event was renamed after saving and the current name finds nothing, the name parsed from what you first typed is searched once. Each configured finder in `src/server/events/details.ts` searches a window around what you gave (the date ±1 day, the month, or the year):
   - Ticketmaster: listings whose name has every word you typed; a festival listed per day is grouped by name and venue into one start and end date.
   - setlist.fm: shows by an artist of exactly that name on the date (or in the year), with venue and city.
   - Clashfinder: the edition matched in its event list (same rule as the lineup adapter), giving the start date.
   - Brave web search (`braveFinder`, when `BRAVE_SEARCH_API_KEY` is set): one query (`"<name>" <date or month or year> <venue> <city>`). A result counts only if its title and description name every word of the event; every full date written there (`findDates` in `parse.ts`) inside the window becomes a candidate whose source keeps the quoted words. These snippets only confirm stage 1 dates; they are never lineup evidence.
   - Gemini, only on "Look again with Gemini" (`{ useGemini: true }`; `geminiReader` in `src/server/events/detailsGemini.ts`, a `DetailReader`): the pages the other finders' web results came from plus the Brave results that name the event, never AXS. A page is sent to Gemini only if its text names every word of the event (and the year, when known); at most 3 pages, one call each, through the same `QuotaLedger` as stage 2. Gemini returns the words the page uses for the date (`dateQuote`) and the place (`venue`, `city`, `country`, `placeQuote`; `details@1`). `checkedCandidate` keeps the page only if the date quote is on the page and `findDates` reads a date inside the window from it; a place value is kept only if it is in a place quote that is on the page (`isVerbatim`). The candidate's source has `readBy: 'gemini'` and both quotes. Out of quota (the ledger refuses or Google answers 429) it stops reading and notes it in `details.notes` (`gemini: ...`, shown on the event); nothing else reads in its place.
   Candidates on the same start date are merged, each field keeping the source that gave it. A failing finder is noted and the others still count. Sources write cities `City, ST` in the US and Canada (`cityLabel` in `src/server/events/place.ts`, from the region a source gives) and as the city elsewhere; an event stores the city and the state apart (see **City, state and country** below).
4. **Place from pages.** Search snippets give dates, not places. For the candidates that will be applied or shown, if a venue or city is missing, the pages that gave the date are fetched (at most 3 per research, never AXS) and their schema.org Event markup (`application/ld+json`) is read in code (`placeFromPage`): an event whose name or a performer has every word of yours, on a day the candidate covers, gives `location.name` as the venue and `addressLocality` plus `addressRegion` as the city. Several matching events at different places give nothing. The page is added as its own source for those fields, with the venue and city as the quote; it does not count as another date confirmation.
5. **Decide.** No candidates: `none`. If you gave a full date and one candidate covers it (or one covering candidate has more sources than any other): `matched`. The date is shown as confirmed with each source and quote, and the candidate fills only empty fields. Otherwise `choose`: up to 5 candidates wait for your pick (`POST /api/events/:id/details/pick`), which fills date and place from the candidate (the name stays yours), or for "None of these". Research never replaces a filled field; where the confirmed candidate differs from a saved field, the event view offers "Use … from <source>" under it, which takes just that field (`{ candidateId, fields }`).
6. **Edit** (`PATCH /api/events/:id`). Any field you change becomes a `user` source. `kind` (`concert`, `festival`, or `null` to go back to the rule) is your choice of type; seen acts may carry a `role` (`headliner` or `support`), kept as yours (`roleFrom: 'you'`) unless it is the lineup's role sent back. In the event view, "Last day" shows the start date until you change it (so the date picker opens on the right month) and is stored only when it differs; venue and city suggest what you have entered on other events (picking a venue you always gave the same city for fills an empty city), and city also suggests places from the Open-Meteo geocoding API as you type (`GET /api/places/cities`, `citySuggestions`). Suggestion fields (series, venue, city, and the Fill gaps editors) list their suggestions under the input while it has focus (`SuggestInput`, `suggestionsFor` in `src/services/format.ts`: the first eight when empty, else matches by `matchNames`) instead of a browser `<datalist>`, which phones barely show; a tap fills the input and saves it as if typed. Seen acts, companions, days attended, rating, ticket price and notes are edited the same way. Typing a seen act offers acts you entered on your other events (`pastArtistNames`, `matchNames` in `src/services/format.ts`: names starting with what you typed first, then names with a word starting with it, in the spelling you used most); Enter alone adds what you typed. Typing a companion does the same with people you entered on your other events (`pastCompanionNames`). Format is edited the same way, as chips: it can hold several values, stored in the one `format` text column separated by commas (`formatsOf`, `joinFormats` in `src/services/format.ts`), so the CSV and the sheet keep it in one column; typing offers formats from your other events, then a starting vocabulary. The Table's Format filter matches any one of an event's formats. "Days you went" sits under the dates. No days stored means you went every day: each day shows ticked, you untick the days you missed, the last ticked day cannot be unticked, and ticking every day again stores none. A seen act can carry `favourite` (your set of the night); `cleanSeen` keeps the mark on the first act only, and `mergeSeen` keeps it through a lineup review. A seen act can also carry `set` (`dj` or `live`) and `b2b` (the keys of the other acts on this event it played B2B with), both yours only (`src/server/events/seen.ts`). `cleanSeen` makes B2B links symmetric and joins chains into one group (`withB2b`), drops partners not on the event, and `mergeSeen` keeps both marks through a review. An act in a B2B can also carry `solo` (it played on its own at the event too) and `soloSet` (that set's DJ or live mark); `setSolo` turns it on or off, and when the act is no longer in any B2B, `withB2b` keeps the solo set as the act's plain `set` and drops `solo`. `seenSlots` adds a solo slot after the B2B (`asSolo`, keyed by `slotId`). Each act in a B2B stays its own seen act, so every count credits each artist; `seenSlots` and `slotLabel` only group them for display ("A b2b B (DJ set)"). Every client patch of `seen` is built with `toSeenInput` so a change to one act never drops another's marks.

**Series** (`LoggedEvent.series`, migration `0009_event_series.sql`). Your name for the festival or tour an event is one edition of, set through `PATCH /api/events/:id` (`series`, `null` clears it). `eventTitle` in `src/services/series.ts` shows an event in a series as "<series> <year>" everywhere the app names it, adding the town of the event's stored city (`townOf`, the part before the comma) when the series name does not already contain it (`withPlace`); `name` is unchanged and is still what stage 2 reads, so the canonical `event_series` is not affected. The Series panel (`SeriesPanel`, in the Manage tab's Series list; the Table's Series button opens it there) offers groups from `seriesSuggestions`: events whose names are equal once `seriesBase` takes out the year (`2024`, `'24`, not a year right after "the"), and a weekend, day or night number, and whose city has the same town, that are not all in one series yet. An event with no city is grouped with the one town its name is known in, if there is exactly one; otherwise it is left out. The name offered is a series you already use for that key, else your most used spelling with the town added (`withPlace`), so one festival in two cities becomes two series. Linking saves each ticked event through the event route, one request per event. The panel also renames a series for all its events (in Manage, through the series record's rename), adds another event to it, or takes one out; the event view has a Series field with your series and the name's base as suggestions. `LoggedEvent.weekend` (1 to 9, `PATCH` `weekend`, `null` clears it; migration `0011_event_weekend.sql`) is the weekend of a festival that runs more than one; `eventTitle` appends " · Weekend N". It is picked on the event or per row in the Series panel, where the default is what `weekendFromName` reads from your own name for the event ("Weekend 2", "Wknd 2", "W2"), saved only when you link. A `Weekend` CSV column is read back on import. An event's series tag in the Table filters to that series in one tap.

**Artist in the title.** Outside a series, `eventTitle` puts the event's main acts first when there are one or two of them (`artistsOf`: seen acts not billed as support) and `eventScale` does not make it a festival: "<act>, <act> - <name>", or "<act> b2b <act> - <name>" when the two are marked B2B. Views render it with `EventTitle` (`src/components/EventTitle.tsx`, from `eventTitleParts`): the acts at the usual weight, the event's name after them a little softer. The name is shown as typed when it already contains one of those acts (compared with `seriesKey`). `name` never changes; the event view shows the title under "Shows as" when it differs.

**Set times.** `mergeLineup` keeps one `CandidateSource` per page and act, with every set that page times for it (`sets`: day, stage, start, end; Clashfinder gives them). They are stored inside `performances.sources`, so they stay cited and need no column. The event view shows each seen act's stage and time (`actSets`, `setLabel` in `src/server/events/sets.ts`), narrowed to the days you went when you gave them. Lineups confirmed before this have no set times until they are looked up again.

**City, state and country.** An event stores `city` ("Las Vegas"), `region` (the state or province: the postal code in the US and Canada, in full elsewhere) and `country`, each with its own source. `splitCity` / `splitEventCity` in `src/server/events/regions.ts` (shared with the browser) split a city written with a US or Canadian postal code ("Las Vegas, NV", "Austin, TX, USA") into city and state, and fill the country that code belongs to when none is stored; the split part keeps the city's source. Nothing else after a comma is touched. It runs on capture, on every edit of the city (where the state you just typed replaces the stored one), when a source's city is taken, and in both stores on read and write, so rows saved before the State column (migration 0010, which splits them the same way) read back split. A US or Canadian state you type fills an empty country the same way. `cityWithRegion` writes "Las Vegas, NV" back for display, the Table's city filter and sort, the Map, Stats and Artists counts, weather, and the lineup and research queries. Anything a postal code can't settle is looked up only on request: `GET /api/places/guess` (`placeGuess` in `place.ts`) asks the Open-Meteo geocoder for populated places by that name that fit any state or country you wrote, groups them by state and country, and gives one when there is a single group or the biggest is at least ten times the next (Las Vegas, NV over Las Vegas, NM); otherwise a note says why. The event view offers it under State and Fill gaps ("State & country") for many rows with "Use" and "Use all"; `placePatch` (`src/services/table.ts`) fills only the missing parts, so nothing you typed is replaced.

**Weather** (`src/server/events/weather.ts`). Only when you ask (`POST /api/events/:id/weather`, or "Weather" in Fill gaps). It needs a start date at least 5 days past and a city. The city is placed with the Open-Meteo geocoder only when exactly one populated place matches it as written (`placesFor`: the "City, ST" or "City, Country" label, or a bare name shared by no other place); otherwise it says why and stores nothing. The Open-Meteo archive then gives each day's high, low, rain and WMO code (up to 14 days), stored as `LoggedEvent.weather` with the place, coordinates and the archive URL.

**Upcoming events and attendance** (`src/server/events/attendance.ts`, shared with the browser; `LoggedEvent.attendance`, migration `0012_event_attendance.sql`). An event can be added before it happens. `newEvent`, `eventFromImport` (a ticked email show still ahead) and `applyPatch` (when an edit or a list import sets dates that are all after today, `isAhead`) store `attendance: 'planned'`; nothing else sets it. You answer in the event view (`WentCard`): `PATCH` `attendance: null` means you went, `'missed'` that you didn't, and `'planned'` puts it back. A stored `'missed'` survives date edits. `attendanceOf(event, today)` works out the state each time: `went` (no value, and not dated ahead, so rows saved before planning existed still wait while ahead), `upcoming` (planned, last day after today, `lastDay` reading a month or year as its last day), `confirm` (planned, last day today or earlier, or no date left) and `missed`. Only `went` events count: `wentTo` filters what the Stats view (`pastEvents`), the Ranking view, the Map, the header's artist count, the home tiles (`homeSummary`) and the Table's summary (`summarize`) see, and Fill gaps does not ask for who you saw, a favourite or a rating on the others. The home lists `confirm` events under "Did you go?" and counts them in its needs chips; the Table shows a badge for every state but `went` in its Details column (not beside the title) and filters on it (`went=` in the address); Stats says how many are waiting. In `WentCard`, "Yes" saves `attendance: null` at once and then offers the event's seen acts (ticked) and the confirmed lineup's acts (unticked) as one-tap chips, the days you went for a multi-day event (`DaysWent`), and "Review the lineup" when one is waiting; nothing is ticked that was not already on the event. The CSV and the sheet carry a worked-out `Went` column (Yes, Upcoming, Not confirmed, No) that is not read back, so sync never changes attendance. Migration 0012 marks rows already saved with a date ahead as planned.

## Artist, Supporting and type

**Act names** (`src/server/lineup/actName.ts`). Before grouping, `mergeLineup` reads each claim's name with `readActName`: "A b2b B" (also "B2B", "back to back") becomes one claim per act, each keeping the whole quote, and the acts' candidates carry `b2b` (each other's keys); a "DJ Set" suffix is dropped from the name and the candidate carries `set: 'dj'`. Confirming copies both onto ticked seen acts; a set type picked in review (`ReviewedPerformer.set`, `null` for none) replaces yours, otherwise `mergeSeen` keeps your earlier marks. The name shown is your most-used spelling of the same normalized name (`yourSpellings` over your seen acts), else the source's, put in Proper Case when it is all one case (`preferredSpelling`; one-word names of up to three capitals and DJ/MC stay as they are).

**Billing roles** (`src/server/lineup/billing.ts`). A role is read in code from a title a source wrote. `splitBill` finds the first marker (`with special guest(s)`, `special guest(s)`, `supported by`, `support from`, `w/`, `with`, `plus`); `billingFromTitle` gives the acts before it `headliner` and after it `support`, but only when a billed act is named on each side, so "An Evening with Bonobo" and "Fred again.. & Four Tet" give no role. The Ticketmaster adapter (`ticketmaster@2`) applies it to each listing's name and attractions and keeps the listing name as the claim's quote. `mergeLineup` keeps a role only when every claim that states one agrees. Review sends each act's role (`ReviewedPerformer.billing`, `null` for none); confirming stores it on the performance and on the seen act, with `roleFrom` `lineup` when it matches the sources and `you` otherwise. Clashfinder and setlist.fm give no roles; Gemini-read pages may (below). "Artist" is every seen act whose role is not `support` (`artistsOf` in `src/services/format.ts`); "Supporting" is the rest.

**From the event name** (`src/server/events/artists.ts`). `GET /api/events/:id` returns `suggestions`: acts named in the event's own name (whole words, after normalization) that a source lists for this event: the performers on the stage 1 candidate the event was matched to (Ticketmaster attractions, the setlist.fm artist; `DetailCandidate.performers`), the lookup's candidates, or the confirmed lineup. A marker in the name gives the role, by the same rule. The same list includes acts you saw at your other events whose name (4+ characters) appears in this one (`pastArtists`). `GET /api/events/:id/name-artists` adds parts of the name (`titleParts`: before a subtitle, without a year, split on billing markers, "b2b" and commas; "Above & Beyond" stays whole) that MusicBrainz knows as an artist of exactly that name with a score of 95 or more (`artistNamed`), at most 4 requests through the rate-limited fetcher. The event view offers each as one tap; nothing is added on its own.

**Roles from pages.** Gemini may return `billing` for a name (`extract@5`); it is kept only when `quoteBacksBilling` finds it in the quote: the nearest role word before the act ("Headliners:", "Support:", "special guest", "opener") names that role, or a marker puts the act on that side.

**Concert or festival** (`src/server/events/scale.ts`, shared with the browser). `eventScale(event, lineupFacts)`: your `kind` wins; otherwise festival when the end date is after the start date, more than 5 acts are known (confirmed lineup acts that were not cancelled, or seen acts), or the edition or the confirmed stage 1 date came from Clashfinder; concert when a confirmed lineup has 1 to 5 acts; otherwise not known. `GET /api/events` returns `editions` (per event: `{ acts, clashfinder }`, from `LineupStore.editionLineupFacts`) so the Table can work it out without loading each lineup. Only `kind` is stored, so the answer follows the event's dates and lineup.

## Stage 1 from email

Ticket confirmation emails are a stage 1 source for back-filling past shows. They propose events; you decide which ones you went to. Code: `src/server/events/email/` and `src/server/events/importRoutes.ts`.

1. **Feed.** Something with access to your mail posts raw messages to `POST /api/imports/email` (`{ emails: [{ id, link?, from, sentAt, subject, html?, text? }] }`, at most 100 per call, `Authorization: Bearer <IMPORT_TOKEN>`). Today that is Claude, reading Gmail through this project's connector and searching ticket senders. The feeder only copies messages; it interprets nothing. Without `IMPORT_TOKEN` the route answers 503.

   **Check email** feeds the same pipeline from the app itself, so you can catch up on new tickets whenever you like. You connect Gmail once ("Connect Gmail" in the review panel: Google sign-in, read-only `gmail.readonly` scope, `GET /api/gmail/connect` then `/api/gmail/callback` with a one-time state); the refresh token is kept in `app_settings` under `gmail`. "Check email" (`scanStep` in `email/scan.ts`) searches Gmail once per seller that has a reader (`sellerQuery`: `from:` its `domain`, plus the reader's `search` words for sellers whose domain also sends ads, such as Live Nation and TicketWeb) for mail received after the newest message that search already read, minus a day so late-arriving mail is not missed. A further search finds forwards (`forwardQuery`: a Fwd subject naming a seller's domain, not sent by you). Each search has its own cursor (`sellers` by domain, and `forwards`), so a newly added seller, or forwards, are searched through all your past mail once. A seller that already has rows on the review list when its cursor is first made starts from the shared watermark the earlier checks kept (top-level `scannedThrough`, now the furthest any search has read, for the page). The cursors, the time the last check finished, and the ids read within each cursor's day of lookback (so they are not read twice) are kept in `app_settings` under `email_scan`. Before the first check the watermark is the newest email already on the review list. Messages are read oldest first, four per request (the Workers CPU limit), and the page calls `POST /api/imports/scan` again until nothing remains; a check that stops halfway resumes where it left off. Gmail is searched once per check: the ids left to read are kept in `email_scan.queue`, so each later call only reads its four messages (Gmail limits how fast an app may ask); an unfinished check searches again after 30 minutes. Google's reason is shown with any Gmail error. When Gmail asks to slow down (429, or 403 `rateLimitExceeded`), the call answers 429 with `retry`, and the page waits 15 seconds and carries on, up to five times. A 403 for a missing permission asks you to connect Gmail again. A message Gmail will not hand over (404, or another 403) is skipped and counted, so it does not stop the check. Found shows land on the review list unticked, like any other import. Needs `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (a Google Cloud OAuth web client whose redirect URI is `<APP_URL>/api/gmail/callback`, published "In production" so the sign-in does not expire after 7 days) and migration `0006_app_settings.sql`. Without the keys the button is not shown.

   **Browser scan** (`src/components/BrowserScan.tsx`, below Check email) runs the new engine, `@livearchive/ticket-scanner` (`packages/ticket-scanner`, a local `file:` dependency), in the page itself. It asks Google for a short-lived `gmail.readonly` token (Google Identity Services token model, `GOOGLE_CLIENT_ID` from `GET /api/imports/scan`; the OAuth client must list the site as an authorized JavaScript origin), runs `scanGmailInBrowser` over Stream A (seller senders) and Stream B (ticket words, `.pkpass`), and revokes the token when it ends. Mail bodies never reach the server: `POST /api/imports/proposals` takes `{ proposals, messages, updatedCursors? }` (only what was read, each value with its quote) and `mergeProposals` (`email/proposals.ts`) folds them into `email_imports` the way every import does: a value fills only an empty field, rows you added or skipped keep your choice, the same mail twice changes nothing. Its own two cursors live in `app_settings` under `email_scan_browser` and move only when "Check for new tickets" sends them. "Full re-scan (ignore watermark)" reads all past mail and never moves them. Every run saves what it finds straight into the review list; there is no dry-run option. The report shows: emails examined, proposals, by seller, unreadable (subject and link), skipped (no receipt wording), flagged, and net unique events (`summarizeScan`). `packages/ticket-scanner/tests/zeroCursor.test.ts` runs the whole synthetic corpus through this path from empty cursors against a fake Gmail (both streams, pages, `after:`) and checks it reads each message once, finds what `scanEmails` finds from the same mail, reports counts that add up, gives the same report on a full re-scan from saved cursors, and sends the token only to Gmail in the `Authorization` header.
2. **Read** (`readEmails`). Each message goes to the reader for its sender's domain (`EmailReader` in `email/types.ts`; one file per seller: Ticketmaster, Live Nation (its order card is Ticketmaster's, plus "View your mobile tickets" with "Mon, Oct 07 @ venue, City, ST"), Tixr, DICE, Resident Advisor, Eventbrite (including its 2013 and 2015–2018 layouts), AXS, Front Gate, TicketWeb (the confirmation's order summary and the tickets email's event details; reminders and event updates are not read)). The HTML is turned into the lines you see when you open the email (`htmlToLines`), and the reader copies the name, date, venue, city, order number, ticket count and total from fixed positions in the seller's layout, each value with the words it came from. No Gemini. Mail a reader does not recognise (ads, reminders) is ignored; a message whose subject announces tickets but whose body does not fit the layout is kept as `unreadable`, so you can open it and type it in. Once a newer reader reads that same message into a show, the unreadable row is no longer listed (`reviewList`). Add a seller by adding a reader with a test, never by loosening an existing one. A ticket a friend transferred to you (AXS "You Received Tickets") is read like an order. A ticket email someone forwarded to you (`email/forwarded.ts`) is read by the original seller's reader: the innermost forward header (Gmail's "---------- Forwarded message ---------" or iPhone Mail's "Begin forwarded message:") gives the original sender, subject and send day, and the lines below it are the original. The review row links to the forward you received. A forward whose header gives no readable send day is listed as unreadable, since a date written without a year is counted from that day. Sellers that name the ticket after the show ("DJ_Dave - Artist Presale", "2025 EDC Las Vegas - 3-Day GA Experience Pass") give the part before the last " - " when that part names a ticket type (`withoutTicketType`); the quote keeps the full line.
3. **Dates** (`email/dates.ts`). Sellers often leave out the year ("Sat Aug 29, 10:00 PM"). The year is then the only one, from two days before the email was sent to a year after, in which that day falls on the weekday given. No weekday and no year: no date, and the words are shown as written. A weekday that disagrees with a stated year means no date. A night that ends before noon the next day is one event on its first day.
4. **Group** (`mergeImports`). Messages about one show become one row (`EmailImport`), keyed by normalized name plus start date, else seller plus order number. A message whose order number is already on a row for the same date joins that row even under another name (a Front Gate receipt says "Second Show Added!", its tickets "(Saturday)"). A later message fills only empty fields. Refund, cancellation and transfer messages add a flag to the row with the same seller and name whose latest order came before them (a club night sold under one name every month gets only its own refund); one that arrives before its order is kept aside (status `flag`, never listed) until the order is read. A row whose date and name (equal, or one containing the other) match an event already in your log is linked to it and not offered again.
5. **Review** (`ImportReview`, opened from "N events found in your email" on the Events view). Rows are grouped by year and start unticked, because a ticket is not proof you went. Shows still ahead are listed apart; ticking one adds it as an upcoming event (planned, see Upcoming events and attendance), and unticked ones stay listed. "Add" turns the ticked rows into events (`POST /api/imports/add`); "Leave these out" marks them skipped (you did not go, or it was not a show at all) (`POST /api/imports/skip`, undoable).

   **Merge into an event you entered** (`mergeIntoEvent`, `POST /api/imports/merge`). When a row is a show you already typed in but the app did not match (a different name, no date yet), "Same as one of my events" on the row opens a picker of your events, nearest date first; a row already matched to your event offers "Merge into this event". Merging links the row to that event (status `added`) instead of making a new one, and follows the sync rule that newer edits are never overwritten: the email fills only the date, end date, venue, city and ticket price you left empty, each sourced as `email` with its link and quote. A field you filled stays as it is, and where the email says something different the review lists it as kept ("Kept yours: venue (the email says …)"). A start date is not filled when you gave a different year, the end date only alongside the email's own start date, and a price only where you never set or cleared one. Personal fields are untouched. The row records the fields it filled (`mergedFields`), so Undo (`POST /api/imports/unmerge`) clears just those, and only where the field still holds that email's value; anything you changed since stays, and the row goes back on the list.
6. **Save** (`eventFromImport`). The event gets the name, dates, venue and city from the row, each field sourced as `email` with the message link and the quoted words; details status `resolved` when dated, else `needs_date`. Personal fields (seen acts, rating, companions, notes) stay empty. The ticket price is the exception (R1.13): `ticketPriceOf` divides an email's dollar total (fees in) by the ticket count the same email gives, and the first email on a row that gives both sets the row's `ticketPrice`, quoted as "$40.00 for 2 tickets". The event takes it with an `email` source (`sources.ticketPrice`). `pricesFromImports` gives the same price to an event already in your log that a row is linked to, when it has no price and no `ticketPrice` source; a price you type or clear is marked `user` and never replaced. It runs on Add, on posted mail and on every Check email step. Check email also reads the order emails of rows that have no price once more, for the price only (`email_scan.prices` keeps the ids read until all have been). Counts come only from the email: Ticketmaster and Live Nation from one "Sec, Row, Seat 5 - 8" line, AXS from an order table with one ticket line, Front Gate from a receipt selling one item that is not a shuttle or parking.

## Importing a list

A list of past events you kept elsewhere (a Notion database export, a spreadsheet, this app's own CSV export) is your own record, so its fields count as typed by you, personal ones included. Code: `src/services/listImport.ts` and `src/components/ListImport.tsx`, opened from "Import a list" in the Table view. It runs in the browser and writes only through the existing routes; no model is involved and nothing is stored until you press Import.

1. **Read** (`readList`). Columns are mapped by header words (`Event`/`Name`, `Date`, `End date`, `Year`, `Venue`, `City`, `State`/`Region`/`Province`, `Country`, `Artist`/`Saw`, `Attendee`/`Went with`, `Rating`, `Ticket price`, `Notes`); others are listed as not imported. Dates are read only when full and unambiguous (`2024-05-17`, `May 17, 2024`, `17 May 2024`, and ranges joined by `→`, `–` or ` to `); anything else stays unread and is flagged. A row with no date takes the year written in its name, as capture does. `City ST` and `City, ST` are split into city and state (`splitCity`, without filling a country the file doesn't give). List cells split on `;` when present, else `,`. Rows with the same name and date are combined into one.
2. **Flag, never fix.** Each row lists what looks wrong: a date it could not read, a name whose year differs from its date, a `?` between letters (a character the export lost, such as `K?D`), no date. The value stays as the file has it.
3. **Match** (`findMatches`), against your log and the open email review rows (status `new` or `skipped`, not yet linked). The same event is the email rule: the same start date and the same name or one containing the other; without dates, the same name and year. It is folded in by default. Another name on overlapping days ("EDC 2022" and "EDC Las Vegas") is offered as a possible match and the row waits until you choose same event, new event, or don't import.
4. **Merge** (`fillPatch`). Folding into an event fills only its empty fields and appends acts and people it does not list; nothing already there changes. A matching email row is first added through `POST /api/imports/add` (restored first if you had skipped it), so the event keeps the email's fields and links, then filled from the list.
5. **Save** (`runImport`). A new row is saved with `POST /api/events` (its name as the line) and then `PATCH /api/events/:id` with every field from the file, clearing whatever the capture parse read out of the name. Details research is not started; it can be run from the event. "Went with" names you mark as yourself are left out.

The app is the source of truth: a list only adds to it. Rows from this app's own export carry an `ID` column; a row whose ID is an event in your log skips matching and is folded into that event the same way (`fillPatch`), so it fills only what the event lacks and never changes or clears a value, an act or a person already there. Such a row that adds nothing is only counted. Acts and people are compared by their records (`GET /api/entities/names`: artist and person names and aliases to record IDs, see Data model), so a row naming someone already on the event under another of their names ("Joel Zimmerman" for deadmau5) does not add them again; without the entity tables names are compared as written. `Format` is read too: it is your own words from your own list.

## Google Sheets sync

A Google Sheet you link in the Table view ("Google Sheets", `src/components/SheetSync.tsx`) is a copy of your log, written one way: the app is the source of truth, and nothing typed in the sheet is read back into the app. To bring events from a sheet in, download it as CSV and use Import a list (above).

- **Sign-in.** The same Google client as Check email (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`), asking for `spreadsheets` and your address, with its own refresh token in `app_settings` (`google_sheets`), separate from Gmail's. Google sends the sign-in back to `/api/gmail/callback`, the address already registered; `sheetsRouter` (`src/server/events/sheetRoutes.ts`, mounted before the imports router) takes it when the state starts with `sheets-` and passes anything else on. The Google Cloud project needs the Google Sheets API turned on.
- **Link.** Paste a sheet's link (the tab open in it, from `#gid=`, is the one written; otherwise the first tab), or make a new sheet with an `Events` tab. Only that tab is read or written (`src/server/events/sheets.ts`).
- **Update the sheet.** The tab is rewritten from your whole log (`eventRows`, the CSV's columns), and the rows written are kept in `app_settings` (`google_sheets_base`). Before writing, the tab is read (unformatted; `sheetTable` turns date serials back into `YYYY-MM-DD`) only to compare it with that base: `outsideEdits` counts rows edited, added or removed in the sheet since the app wrote it (every row with data, for a tab the app never wrote). When there are any, or columns of your own that the rewrite would remove, you're told and asked to confirm; otherwise the tab is written straight away.
- **Nothing lost by surprise.** The write is refused (409) when the tab changed since it was read (`sheetVersion`). A tab with data but no `Event` or `Name` column is never overwritten.

## Artist genres

Genres of the acts you saw, so the Stats and Ranking views can show what kind of music you go out for. Code: `src/server/events/genres.ts` (shapes in `genreTypes.ts`), routes in `genreRoutes.ts`, the browser side in `src/services/genres.ts` and `src/components/ArtistGenresPanel.tsx` ("Genres" in the Table view). Nothing is guessed and no model is involved; an act neither source knows has no genre, and the views count it apart.

1. **music-story file.** music-story (a separate repo: your 19.5 years of Spotify and Last.fm listening in DuckDB, on your Mac) writes `build/artist_genres.json` with `uv run python -m pipeline.artist_genre export`: every artist it knows with a genre (name, MusicBrainz ID, styles with weights summing to 1, which tag sources fed it: Last.fm, Spotify, MusicBrainz) and its curated genre map (tag to style and one of 13 parent genres). You upload it in the panel (`POST /api/artist-genres/music-story`). Each act you saw is matched by its stored MusicBrainz ID (`canonical_artists.mbid`), then by name (`normalizeName`, with your renames from `artist_aliases`). Only matched acts are stored, as `artist_genres` rows with source `music-story`; uploading again replaces them. The genre map is kept in `app_settings` (`genre_map`).
2. **MusicBrainz, on request.** For acts the file does not cover, "Look up on MusicBrainz" sends 5 at a time (`POST /api/artist-genres/musicbrainz`). Each uses the stored MusicBrainz ID or the one artist whose name or alias is exactly the act's name (`exactMatches`, the rule `resolveArtist` uses); two or more, or none, means no genre. The artist's genres (`/ws/2/artist/<id>?inc=genres`, with vote counts) are read through the genre map: unmapped tags are ignored, styles under 15% of the votes dropped and the rest rescaled (`mapTags`, the same rule as music-story). The row keeps the artist page as `source_url`. A lookup that finds nothing is stored too (empty `genres`), so it is not repeated.

3. **You.** In the event panel, under "Who you saw", the Genres list (`src/components/SeenGenres.tsx`) shows each act's genres with an "Add genre" field that offers every genre you already have as you type (`knownGenres`: the genre map's styles and those stored on acts, yours included); anything else is added as a new genre, which is its own parent genre. Adding or removing a genre makes the act's genres yours (`PUT /api/artist-genres/:key`, `setOwnGenres`): the shown ones are copied and changed, stored as source `you` with equal weights. A known genre keeps its spelling and parent. "Use music-story's" (or MusicBrainz's) drops yours so the found ones show again.

Which to show (`genresByArtist`): yours when you set any (an empty list of yours means you say none), else music-story's genres when it has any, else MusicBrainz's. Stats ("Genres you see live", `genreMix`): every act you saw at every event you went to counts once, split across its genres by weight; the share is of the sets with a genre, and the rest are counted apart. Artists: each card names up to three styles (the tooltip gives the weights and the source), and a genre filter lists the parent genres present.

## Sources

Each source is an adapter in `src/server/lineup/adapters/` implementing `SourceAdapter.collect()`. An adapter returns stored documents, performer claims, fact claims and documents that need extraction. Adapters that are not configured are skipped and reported in the job log.

| Adapter | What it gives | Access | Evidence |
| --- | --- | --- | --- |
| `clashfinder` | Acts per edition with stage, day and set times; past years stay archived | Free account. Every call is signed with `authUsername` + `authPublicKey` (SHA-256 of username, private key and parameters) | `crowd` |
| `promoter` | Official lineup page text (Insomniac, Goldenvoice, ...); for past editions the Wayback Machine snapshot closest to the event dates | Public pages; no key | `billed` (after Gemini extraction) |
| `ticketmaster` | Canonical name, dates, venue and attractions for upcoming or recent events | Free Discovery API key, 5,000 calls/day | `billed` |
| `setlistfm` | Post-show setlists that upgrade an act to "performed" | Free non-commercial key | `performed` |
| MusicBrainz (`musicbrainz.ts`) | Stable artist IDs, resolved in the background after you confirm; artist genres only when you ask (Artist genres) | No key, 1 request/second | n/a |
| Web search (`search.ts`) | Stage 2: candidate lineup URLs when every source came back empty (stage 1 date checks are in `events/details.ts`): Brave Search API when `BRAVE_SEARCH_API_KEY` is set, otherwise Gemini grounded search (needs a billed Gemini project) | Brave free plan, or Gemini quota | Pages are fetched and extracted like any other; snippets are never evidence |

AXS is deliberately excluded as a lineup source: it has no public discovery API, and scraping it breaks its terms. Your own AXS ticket emails are read like any other seller's (stage 1 from email); nothing is fetched from AXS.

Clashfinder's event list is keyed by slug; the readable title is `desc` and `startDate` is Unix seconds. One edition often has several slugs (`edc2026`, `edclv2026`, a livestream clash), so the adapter takes the most-edited public clash whose title contains every word of the event name (or whose slug starts with them) and whose start date is in the year. Private clashes and fantasy or predicted lineups are skipped because they are guesses.

Promoters overwrite their lineup page for the next edition, so a past event never reads the live page unless you gave that URL yourself and no snapshot exists. The Clashfinder hash format could not be verified when the adapter was written; it is configurable through `CLASHFINDER_HASH_FORMAT`, and `CLASHFINDER_PUBLIC_KEY` accepts a ready-made key.

Job logs and errors are shown in the UI and stored, so credentials are redacted from them (`redactSecrets` and `redactUrl` in `http.ts`).

All HTTP goes through `createRateLimitedFetcher()` (`src/server/lineup/http.ts`), which spaces requests per host (MusicBrainz 1.1 s, Clashfinder 1 s, setlist.fm 0.6 s, Open-Meteo 0.2 s) and sends a User-Agent with `CONTACT_EMAIL`.

## Lookup pipeline

A lookup is a `LookupJob` that moves through stages, saving after each one (`src/server/lineup/pipeline.ts`).

1. **Create.** From the app, a lookup starts on a saved event (`POST /api/events/:id/lineup`): its name, year, dates, venue and city become the input, an optional lineup URL can be added, and the job keeps the event's id (`LookupJob.eventId`). Event name and year are required. The edition key is `series-slug/<start date>` when the date is known (an artist plays many nights a year, each with its own openers), otherwise `series-slug/year`. If a confirmed edition exists under that key, or under the year key with the same start date (editions confirmed before dates were part of the key), the job is ready for review immediately (`candidate.cached = true`).
2. **collect.** First wave (Clashfinder, promoter, Ticketmaster) runs in parallel. The second wave (setlist.fm) runs with dates and city filled in from the first. Every response is stored as a `SourceDocument`; every act as a `PerformerClaim`. A failing adapter is logged and does not stop the others.
3. **extract.** Each unstructured document (promoter or archived page) gets one Gemini call. The prompt includes one confirmed example from the same website when one exists. Names failing the verbatim check are dropped and counted in the log. Progress is saved per page, so a quota pause resumes where it stopped. Extraction cache: when an earlier job for the same edition key already read the same document (same URL and content hash) with the same model and prompt version, its claims are copied to the new job, each re-checked with `isVerbatim`, and Gemini is not called (`findExtractedClaims`). A page whose text changed is a new document and is read again; a new prompt version reads everything again.
4. **discover.** Only when there are no claims at all: one web search (`"<event>" <year> lineup`). Up to 6 results are fetched; a page is kept only if its own text names every word of the event and the year, which drops other editions and unrelated pages. At most 3 kept pages go to extract. A result on the event's own domain (its host contains the event name run together, e.g. `sunsoaked.insomniac.com`) is read first and treated as a `promoter` source (also when an earlier run stored it as `discovered`); others are `discovered`. Confirming a lookup with such a page saves it as the series lineup URL, so the next lookup reads it directly. Aggregator pages can list other events' artists verbatim, so when two or more `discovered` pages were read, an act backed by only one of them is flagged for review (`merge.ts`). Brave is used when `BRAVE_SEARCH_API_KEY` is set and a Brave 429 parks the job until its reset; otherwise Gemini grounded search, which has no free-tier quota and is off in `wrangler.jsonc`.
5. **merge.** Claims are grouped by normalized name after applying learned aliases and the blocklist, then scored. Confidence is `1 - Π(1 - r)` over the source types listing the act, where `r` is each source's reliability (a prior, Clashfinder 0.93 above promoter 0.75 and archived pages 0.72, pulled toward its measured accept rate in your reviews). Each source that gave a full lineup for the edition (Clashfinder, promoter or archived page with 5+ acts) and leaves the act out scales it by `1 - 0.4·r` (`missingFrom`), so an act only a promoter page lists falls below the flag line when Clashfinder has the lineup, while a late addition only Clashfinder lists stays above it. Status becomes `needs_review`, or `no_data` if nothing was found.
6. **Review and confirm.** You accept, rename, reject (with a reason) or add acts, and tick who you saw; acts already marked as seen on the event start ticked. Confirmation writes the canonical edition (its facts default to the event's, with gaps filled from what the sources cited) and the learning data, links the event to the edition, and sets the event's seen acts to what you ticked plus any act you had added by hand that the lineup does not list (`mergeSeen` in `learning.ts`). It then queues MusicBrainz ID resolution. "Edit lineup" on a confirmed event reopens the review from the saved edition (`startRows` in `src/services/reviewRows.ts`: kept, renamed, cancelled and hand-added acts as you left them, rejected ones unticked); confirming again rewrites the edition and records corrections, but does not count source accuracy or read source pages a second time. The review can be filtered by day and stage (`filterOptions`).

Job statuses: `queued`, `running`, `waiting_quota`, `needs_review`, `no_data`, `confirmed`, `failed` (after 3 errors with backoff).

## Quota and the queue

- `QuotaLedger` (`src/server/lineup/quota.ts`) counts Gemini calls per model per Pacific day, against `GEMINI_DAILY_LIMIT` and `GEMINI_PER_MINUTE`. It refuses a call before it is made when the budget is spent.
- A Gemini 429 is parsed: a per-day quota parks the job until midnight Pacific; otherwise the job waits for the `retryDelay` Google returns (60 s if none).
- Parked jobs keep everything collected so far. Under Node, the worker (`LookupWorker` in `service.ts`) checks for due jobs every 20 seconds, one at a time. On Cloudflare a Cron Trigger sends due jobs to a Queue every minute and the queue consumer runs them one at a time (see Hosting). "Try now" in the UI retries immediately, past an earlier 429 pause but not past your own daily budget.

## Learning loops

Review is where the system improves (`src/server/lineup/learning.ts`). Nothing retrains a model; every decision becomes data the next lookup reads.

| Your action | What is stored | Effect on the next lookup |
| --- | --- | --- |
| Rename an act | `artist_aliases`: old spelling to your spelling, plus a `renamed` correction | Variants merge in code, no AI call |
| Reject as "not an act" | `extraction_blocklist` per site, plus a `rejected` correction | After 2 rejections on a site, that string is dropped before review |
| Reject as "wrong event" | `rejected` correction, source penalized | Source reliability drops |
| Reject as "cancelled" | Performance kept with status `cancelled` | Sources are not penalized for billing it |
| Accept | `source_stats` accepted count per source, per series and globally | Reliability rises; confidence uses measured accuracy (Beta prior, weight 10) |
| Add a missed act | `added` correction | Shows which sources miss acts |
| Confirm a Gemini-read page | `extraction_examples`: an excerpt plus the confirmed names, up to 3 per site | The next read of that site includes a worked example |
| Confirm with a lineup URL, or with an accepted promoter page | `event_series.lineup_url` | Next year's lookup knows where to look |

Cached editions are not counted again in source stats. Every claim records its extractor and version (`gemini:<model>` plus `extract@5`; every page, the event's own site included, is told to keep only acts billed for that event and year and leave out other events, dates, cities and editions it lists), so claims from a bad model or prompt version can be found and re-checked later from the stored documents.

## Data model

Defined in [`supabase/migrations/0002_source_first_lineups.sql`](supabase/migrations/0002_source_first_lineups.sql) and [`0003_event_log.sql`](supabase/migrations/0003_event_log.sql); both must be applied (the server checks one table from each at start). [`0004_email_imports.sql`](supabase/migrations/0004_email_imports.sql) is needed only for email import; without it the rest of the app works and the import routes fail. [`0005_billing_and_kind.sql`](supabase/migrations/0005_billing_and_kind.sql) adds `billing` to `performer_claims` and `performances` and `kind` to `logged_events`, [`0007_event_format.sql`](supabase/migrations/0007_event_format.sql) adds `format`, [`0008_event_weather.sql`](supabase/migrations/0008_event_weather.sql) adds `weather`, and [`0009_event_series.sql`](supabase/migrations/0009_event_series.sql) adds `series`, [`0010_event_region.sql`](supabase/migrations/0010_event_region.sql) adds `region` (the state) and splits stored "City, ST" values, [`0011_event_weekend.sql`](supabase/migrations/0011_event_weekend.sql) adds `weekend`, [`0012_event_attendance.sql`](supabase/migrations/0012_event_attendance.sql) adds `attendance`, and [`0013_artist_genres.sql`](supabase/migrations/0013_artist_genres.sql) adds `artist_genres` (only the genre features need it), and [`0016_entity_labels.sql`](supabase/migrations/0016_entity_labels.sql) lets `entities` hold labels (only labels need it); apply each before deploying code that writes them. [`0006_app_settings.sql`](supabase/migrations/0006_app_settings.sql) adds `app_settings` (the Gmail connection and how far Check email has read); only Check email needs it. The local file store (`store/fileStore.ts`) implements the same `LineupStore` interface for development.

| Layer | Tables |
| --- | --- |
| Canonical | `event_series`, `event_editions` (unique `key`), `canonical_artists` (normalized key, optional MBID), `performances` (per edition and artist, with status, billing role, confidence and sources) |
| Evidence | `source_documents` (URL, hash, stored body), `performer_claims` (quoted span, extractor, version) |
| Operations | `lookup_jobs`, `quota_ledger` |
| Learning | `artist_aliases`, `extraction_blocklist`, `source_stats`, `corrections`, `extraction_examples` |
| Personal | `logged_events` (one row per event you went to or plan to, with `attendance` `planned` or `missed` until you went (0012): fields (city, state and country apart), field sources, details research, lineup job and edition links, seen acts with their roles and your set and B2B marks, your choice of type, format, series, companions, days, rating, price, notes). The `attendance` and `seen_sets` tables from 0002 are no longer written; [`0003_event_log.sql`](supabase/migrations/0003_event_log.sql) copies them into `logged_events`. |
| Settings | `app_settings` (key → JSON: the Gmail connection's refresh token and account, Check email's watermark). Server-side only; row level security on with no policies. |
| Genres | `artist_genres` (0013: one row per seen act and source, `music-story`, `musicbrainz` or `you`, with its styles and weights, MusicBrainz ID and page; empty genres when checked and none found). The genre map from the last music-story upload is in `app_settings` (`genre_map`). |
| Import | `email_imports` (one row per show found in your ticket emails: status, read fields with their quotes and message links, flags, the event it became). Proposals only; never read as part of your log. |
| Records | `entities` (0014: one row per artist, person, venue, place, series or organization, with a permanent UUID; one live record per kind and normalized name; `merged_into_id` instead of deletes), `entity_aliases` (other names, unique per kind), `entity_links` (venue in place, series hosted by organization), `entity_history` (one manifest per Manage change, for undo). `logged_events` gains `venue_id`, `place_id`, `series_id` and `companion_ids`, and each seen act an `artistId`. |

Records (0014, `src/server/entities/`, contracts in `.spec/SYSTEM_SPEC.md` section 3) are dual-written for now: an event's names stay the source of truth, and `withEntityLinks` (wrapped around the store by `createStore`) points them at records on every save, creating a record for a name not seen before. A name matches a live record of the same kind by its normalized name or an alias (artists also through the pipeline's `artist_aliases`); a place is the event's city with its state and country. New records get an ID derived from kind and name, so racing saves and a re-run agree. Look-alike names (a leading "the", spacing, a place without its state) are never joined on their own: `possibleDuplicates` lists them for you. Events saved before 0014 are linked once by `backfillEntities` (the Worker's minute cron, or local startup), which also copies learned artist spellings into `entity_aliases`. Without the 0014 tables events save with their names only, as before. Both stores enforce the same rules (`entities/integrity.ts`).

A venue that is in a place (`entity_links` role `in`) gives every event there its city, state and country (`src/server/entities/venuePlace.ts`), applied by the linking store on every save and marked `sources.city/region/country = { sourceType: 'venue' }` (shown as "from its venue"). Whatever location the save brought (typed, Stage 1 research, an import) is replaced; when it was another place it is kept on the venue as an offer (`attrs.placeOffers`) for Data health, so nothing is lost and research never overrides the venue. Stored weather for an event whose city changes this way is kept and flagged `cityChanged`, not fetched again. A venue first saved with a city is put in that city. Venues from before this are handled once, after the first backfill: `backfillVenuePlaces` (Worker cron or local startup, setting `venue_places_backfill`) puts in a place only the venues whose events all use one city, filling their events without a city, as one undoable change; venues whose events disagree keep no place, and `GET /api/entities/health` lists them with the cities their events use. Setting a venue's place in Manage rewrites its events the same way (undoable); merging two venues keeps the target's place.

Manage operations (`src/server/entities/manage.ts`, `/api/entities`) change records: rename, merge, add or remove an AKA, link a venue to its place or a series to the organization hosting it, and add an organization by hand (every other record comes from your events' names). A rename or merge also rewrites the name on every event that points at the record, whichever of its names the event used, so text and records never disagree; a rewritten venue, city, state or country is marked as yours (`sources`). The old name becomes an AKA, so typing it again finds the record. A name or AKA another record already has is refused with that record, to merge into instead. Merge points the source (and anything merged into it) at the target, moves its AKAs and links (dropping duplicates), and on an event that had both, keeps one act or person: the target's marks first, the source's filling what it lacks, B2B partners following the new key. Places have no AKA; they merge. Every change writes its manifest to `entity_history` first, then records, AKAs, links and events; undo puts back the records and every event not changed since, and is refused while a later change touched the same records. A renamed artist's acts get the new key, so a canonical lineup still listing the old spelling no longer marks them as seen in lineup review.

The Manage tab (`src/components/ManageView.tsx`, `ManageEntry.tsx`) picks its section from one menu (`MenuButton`, shared in `src/components/ui/`) on the same row as the search box, on the right: the record kinds, then Data health and History. The search box shows on a record list only. It lists the live records of each kind with how many events point at each (from the IDs saved on events), a look-alike badge from `possibleDuplicates`, and a search over names and AKAs. ## Hosting

The `/api` routes live in `src/server/app.ts` and take a `JobRunner` that starts a job without waiting for it. Two hosts wire them up:

| | Node (`server.ts`, `npm run dev`) | Cloudflare Worker (`worker/index.ts`, `wrangler.jsonc`) |
| --- | --- | --- |
| Frontend | Vite middleware in dev, `dist/` in production (pages: the marketing page, the app and the demo, see Public pages) | Workers static assets from `dist/`, unknown addresses get `404.html`; the Worker runs for `/`, the app page, `/demo`, `/robots.txt`, `/sitemap.xml`, `/api/*` and the share page (`/s`, `/s/*`, `/S`, `/S/*`), and hands the pages it lets through to the static assets (`ASSETS`)
| API | Express | The same Express app, through `handleAsNodeRequest` from `cloudflare:node` (`nodejs_compat`) |
| Starting a job | `LookupWorker.kick` runs it in-process | A message on the `concert-tracker-lookups` Queue |
| Due and parked jobs | `setInterval` every 20 s | Cron Trigger every minute sends due jobs to the Queue |
| Store | Supabase, or the file store | Supabase only |
| Config | `.env` | `vars` in `wrangler.jsonc` plus `wrangler secret put` |

Workers Builds (the GitHub-connected build) deploys pull requests with `wrangler preview`, which reads the `previews` block in `wrangler.jsonc`. Previews get the plain settings but no secrets, so their API answers "not configured" and they never touch the Supabase data or start jobs.

The queue consumer runs one message at a time (`max_concurrency: 1`), so the per-host spacing in `http.ts` still holds; the spacing lives in memory, so it is per isolate rather than global. Each queue message runs one step of a job (`runJob` with `oneStep`: one stage, or one page of extraction), saves it back to `queued` and sends the next message, so one invocation stays within the subrequest and CPU limits; running a whole lookup in one invocation went past 50 subrequests after three pages. Duplicate queue messages are harmless because `runJob` skips a job that is no longer `queued` or `waiting_quota`. A run cut off anyway leaves the job `running`; after 10 minutes without a save (`STALE_RUN_MS`, `isStaleRun` in `store/types.ts`) `dueJobs` returns it and it resumes from its last saved step, without repeating pages already read. MusicBrainz artist resolution handles 20 artists per run for the same reason. While a job is between steps the UI still shows it as looking through sources.

Each Worker request may make at most 50 subrequests on Workers Free, and every Supabase call is one. So a request never makes store calls in proportion to a lineup's or a list's size: confirming a lineup gathers its corrections, source stats, blocklist entries, aliases and artists and saves each kind in one call (`addCorrections`, `bumpSourceStats`, `bumpBlocklist`, `putAliases`, `ensureArtists`; a stats or blocklist bump is one read and one write), `upsertEdition` adds missing artists in one upsert, adding email imports saves the events with one `putEvents`, bulk name suggestions read editions with `getEditions`, and `POST /api/events/lineups` takes 5 events per request (Fill gaps sends 50 in chunks). `tests/pipeline.test.ts` checks that confirming 150 acts makes as many store calls as confirming 5.

## Share page

A read-only page of your history at `/s/<code>` that anyone with the link can open without signing in (spec: Share page, 2026-10-28). Code in `src/server/share/`.

- **Links** (`links.ts`, table `share_links`, migration 0015): a code is 16 random bytes as 22 URL-safe characters; only its SHA-256 hash is stored. One link is active at a time; a new one turns the old one off. Settings: display name (yours to set, never in the code), time zone (from your browser), and switches for dates and venues (on) and format (off).
- **What it shows** (`view.ts`, `buildShareView`): the allow-list. The page is rendered from the returned `ShareView` alone: titles, years, city/state/country, Concert or Festival, act names, totals, most seen, series you went back to, cities; dates, venues and format only when switched on. Only events you went to whose last possible day is before today in the link's time zone (nothing today, underway, ahead, undated, planned or missed). No "last updated" date; with dates hidden, events in a year are listed A to Z. The store reads only `SHARE_EVENT_COLUMNS` (`listShareEvents`), so companions, notes, rating, price, weather, sources and the typed line never leave the database.
- **The front door** (`door.ts`, first thing in `worker/index.ts`): any path under `/s` in either case is answered here and never reaches Express or the SPA fallback. Only GET or HEAD of exactly `/s/` plus a 22-character code can open a page; everything else, and unknown or turned-off codes, get the same 404 "not active" page. The page is plain HTML with inline styles and no scripts (`page.ts`), every value escaped, with `Cache-Control: no-store` (turning a link off works at once), a CSP that allows no scripts, `nosniff`, `DENY` framing, `no-referrer` and `noindex`. The route makes no writes and logs only the link id.
- **Second lock** (`access.ts`): with `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` set, every request the Worker sees that is not a public page (see Public pages) needs a valid Cloudflare Access token (`Cf-Access-Jwt-Assertion`: RS256, signed by the team's keys, this application's audience, the team as issuer, not expired), so a path trick past the `/s/*` Access bypass (dot segments are normalized to `/api/...` before the Worker sees them) is still refused. Set both before turning on the bypass.
- **Your controls** (`routes.ts`, `/api/share`, behind Access like the rest of `/api`; Share in the Menu, `SharePanel.tsx`): `GET /share` reads the active link (id, date, settings, never the hash); `POST /share` makes a new link, turning the old one off, and returns its code once; `PUT /share/settings` changes the active link's settings; `DELETE /share` turns sharing off; `GET /share/preview` renders the active link's page through the same code and headers as `/s/<code>`. Because only the hash is kept, the full link can be shown again only in the browser that made it (it remembers it locally); elsewhere you make a new link.

## Multi-user

Built on the branch `claude/multi-user`, **off by default and not applied to the live database**. Multi-user is the only mode that admits anyone but the owner (spec: `multi-user/multi-user-spec-v2-ON-HOLD.md` in the project files; counsel's sign-off and the owner's go-ahead are still needed before turning it on). Code in `src/server/auth/`.

**Access gate (fail closed).** Every `/api` request except `GET /api/health` passes one check, in both modes (`accessGateFromEnv` in `src/server/auth/config.ts`):
- `MULTI_USER=on` (exactly, after trimming): members, as above.
- Unset, blank, `off`, or any other value: single-owner. Only the Access sign-in whose email is `OWNER_EMAIL` gets through; everyone else gets 403, and no sign-in gets 401.
- Missing settings for the mode above, or a `MULTI_USER=on` that is half set: closed. Every `/api` request gets 503 and nothing runs. `GET /api/health` still answers, with its status only.

A broken or missing setting therefore locks the app rather than opening it.

**Local development.** `LOCAL_DEV_OWNER=on` lets the Node dev server (`npm run dev`) answer `/api` without Access, with no sign-in. It is ignored when `NODE_ENV=production`, it is read only by `server.ts` (the Worker cannot enter this mode), the server listens on `127.0.0.1` only, and each request must arrive on loopback with a loopback `Host` and no forwarding header (`localOwnerMiddleware`, `src/server/auth/gate.ts`). Tests: `tests/accessGate.test.ts`.

- **One login** (`requestScope.ts`, `members.ts`): Cloudflare Access is the only login. In `/api`, `memberMiddleware` reads the Access token again (`readAccessClaims`, keys cached, no request), looks the email up in the `members` table (migration 0017; an email not listed, or blocked, gets 403 "not invited" with `code: "not_invited"` and the email, and nobody signs up; a stranger may ask instead, see Request access), and on a first sign-in makes a Supabase Auth user and links it. Members are cached 15 seconds per isolate; refusals are never cached, and the owner's block or removal clears the cache on the isolate that made it. `/s/*` still bypasses Access.
- **A store per request**: the middleware builds `store.forUser({ userId, role })` and keeps it in `AsyncLocalStorage`; the routes keep calling `deps.store`, a stand-in (`requestScopedStore`) that hands each call to the current request's store. Outside a request (queue, cron) it is the system store. `LineupStore.forUser` limits events, email imports, lookup jobs, share links and settings to one member: the Supabase store filters by `user_id`, stamps it on writes and, with a member client holding a 60-second HS256 token minted locally (`supabaseJwt.ts`, `SUPABASE_JWT_SECRET`, `SUPABASE_ANON_KEY`), runs under row level security too (`own_rows` policies); the file store behaves the same for tests. Writing over another member's id is refused. Settings come from `user_settings`; the owner falls back to `app_settings` for settings made before multi-user.
- **Owner-only**: the server Gmail connection and server scans, and the music-story import and MusicBrainz lookup (they use the owner's listening data and genre map) (`ownerOnly`). A member's browser scan (Check email in the page) works. Manage, genre edits and Sheets are per member (below).
- **Lineup lookups for members**: a member can start a lookup (the pipeline reads and quotes sources as ever) and review it. Their review (`confirmLookupForMember`, used by `POST /lookups/:id/confirm` for a member) changes only their own event: ticked acts go into its `seen` (a lineup act as billed, or a typed name as yours), and the event links to the shared edition only if the owner has already confirmed one. It writes no edition, performances, corrections, source stats, blocklist, aliases or series; what the member sees afterwards is a draft built from the sourced acts they accepted, not stored. The owner's review is what teaches the pipeline.
- **Shared on purpose**: lineup editions, performances, source documents, source stats and the other lineup tables are the commons. Only the pipeline writes them, from stored sources with quotes; a member cannot add an unsourced act to them.
- **Jobs and quota**: a job carries `userId` (migration 0017) and its member's spellings are the only ones the merge uses. `dueJobs` hands out jobs in turns by member (`roundRobin`). `GEMINI_USER_DAILY` caps one member's Gemini calls a day and `GEMINI_OWNER_RESERVE` keeps calls back for the owner (both 0 = off); counts are `quota_ledger` rows keyed `<day key>:user:<id>`. A member's own pause is scoped to them (`QuotaExhaustedError.scope`); only a real 429 pauses everyone. No fallback model.
- **Share page**: a link has the member's `user_id`; `door.ts` reads only that member's events for it.
- **Request access** (migration `0024_access_requests.sql`, `src/server/auth/requests.ts`, `requestRoutes.ts`, the request banner in `src/components/SampleBanner.tsx`, the Requests tab in `MembersPanel.tsx`). A signed-in Google account with no members row gets the app in sample mode (see Public pages): the banner shows its verified email, a Request access button, and a switch-account link (`/cdn-cgi/access/logout`). No real data and no counts are shown to it. `POST /api/access-requests` is the one data-changing route a stranger may call. It is mounted before `memberMiddleware`, reads the Access token again, takes the email and `sub` from it (never from the body), and answers `{state: "sent" | "closed"}`. `GET /api/access-requests/mine` answers `{state: "none" | "sent" | "closed"}`. One request per email: a pending, declined or accepted row changes nothing and answers "sent". A banned account is answered the same way as a pending one.
  - **States.** `pending` (asked, no account), `accepted` (member, with a members row), `declined` (banned for life; the members row, if any, is `blocked` and keeps its data), `left` (the member deleted their own account; may ask again, and approval gives an empty tracker). `source` says how the row began: `requested`, `invited` (the owner added the email, recorded as accepted) or `blocked` (the owner banned an email that never asked).
  - **Database functions.** Every change is one `security definer` function with `search_path` set and execute revoked from `public`, `anon` and `authenticated`; only the server's service key can call them (`tests/rls/accessRequests.test.ts` checks the anon and authenticated keys are refused). `access_request_submit` and `access_request_state` answer the stranger; `access_request_set` makes the owner's change (accepted upserts the members row and unblocks; declined and pending block any members row); `access_request_removed` sets the history after a member's data is deleted (declined when the owner deletes, left when the member leaves). Each function writes both tables in its own transaction.
  - **Pause and cap.** The `access_requests` row in `app_settings` holds `{paused, cap}`. Paused, or with `cap` pending requests already waiting (default 20, the owner sets 1 to 100 in the Requests tab), a stranger's ask answers `closed` and inserts nothing. Lowering the cap below the pending count closes requests at once.
  - **Banned by Access sub.** A declined row whose `access_sub` matches the caller's token counts as banned in the request routes only (a new email with the same Google account gets "sent" and no row). `resolveMember` checks `members.blocked` alone.
  - **Owner's actions** (`accessRequestOwnerRouter`, behind the owner check): list the history with the pending count (`GET /api/access-requests`), change any status with `PUT /api/access-requests/:email` (`to`: pending, accepted or declined; the owner's own row cannot change, and `left` is set only by removal), change the settings with `PUT /api/access-requests/settings`. Blocking an accepted member asks for a confirmation and keeps their data. Deleting data asks for the email typed in full (`DELETE /api/members/:email` with `confirm`, and the same on the Worker).
  - **Jobs.** `runJob` checks the job's member before each step (`hasActiveUser`, multi-user only). A blocked or removed member's job is parked with a reason and makes no outside call; it resumes only if the member is accepted again.
  - **Not done here.** No email notification. No per-IP rate limit on the POST: the workers have no rate-limit binding, so the one-request-per-email rule and the cap are the only bounds until a Cloudflare rate-limit rule is added.
  - **Live check** (owner, with a second Google account, before turning it on): ask, see pending; decline, and the account still sees "Request sent" and gets 403; accept, and it gets an empty tracker within 15 seconds; block, and it gets 403 while its data stays in the database; pause, and it sees "closed".
- **Migrations**: `0017_members_and_user_id.sql` is safe while single-owner (adds `members`, `user_settings`, nullable `user_id` defaulting to the owner, RLS; the service key bypasses it). `0018_user_id_backfill.sql` needs the owner's Auth user and `members` row first, then makes `user_id` required and `email_imports` unique per member.
- **Vault** (`src/services/vault.ts`, not used by any screen yet): notes, companions and people's names are meant to be encrypted in the browser. A random 32-byte master secret is wrapped by a PBKDF2 (600,000) passphrase key and by a Base58 recovery key; HKDF gives an AES-GCM field key and an HMAC name-token key. Fields are `v1:<iv>:<ciphertext>`; a passphrase change re-wraps only. People are to be identified by random ids with the HMAC token as a name-to-person lookup (`user_entity_aliases`). Not built: the vault columns, the server's refusal of plaintext notes and companions once encrypted, per-member people, the account export and deletion, the caches, and any screen.
- **Testing**: `multiUserAuth.test.ts`, `multiUserStore.test.ts` (two members through a real Express app, concurrent requests, share page), `multiUserQuota.test.ts`, `vault.test.ts`, `accessRequests.test.ts` (the request routes, refusal codes, settings checks, blocked-member cache, job parking). `tests/rls/rls.test.ts` and `tests/rls/accessRequests.test.ts` (`npm run test:rls`, run one file at a time: `--test-concurrency=1`; needs `RLS_PG` pointing at a Postgres where a scratch database may be made) check row level security and the request functions against a real Postgres; plain `npm test` skips them.

**Vault, account and cache (also on the branch).**
- *Private notes vault.* A member can turn on a browser-side vault (`src/services/vault.ts`, `src/components/VaultContext.tsx`, `AccountPanel.tsx`). The server (`src/server/auth/vault.ts`) stores only wrapped key material (`GET/PUT /api/vault`, `POST /api/vault/rewrap`; PUT works once). Once it exists, `vaultGuard` refuses plaintext notes with a 400, so the server never stores a readable note again. Scope today is **notes only**; companions stay plaintext until the people split. List import encrypts notes in the browser while the vault is unlocked and leaves them out while it is locked.
- *Account.* `GET /api/account/export` returns the caller's events, email imports, share links (no hashes) and lookups. `DELETE /api/account` needs the caller's own email as `confirm`; the owner is refused. Backups keep deleted rows until they expire.
- *Response cache.* With `SOURCE_CACHE=on`, Ticketmaster responses are kept 24 hours (`src/server/lineup/responseCache.ts`, migration 0019, API key stripped from the key). Brave results are never cached because its terms forbid it. Off by default.

- **Per-member records** (migrations `0020_per_member_entities.sql`, `0021_owner_entities_copy.sql`): people, venues, series, aliases, links, history and your own genres live in `user_entities`, `user_entity_aliases`, `user_entity_links`, `user_entity_history` and `user_artist_genres` (RLS `auth.uid() = user_id`, primary keys `(user_id, id)`), plus `logged_events.person_ids`. Manage renames, merges and AKAs write only to the member's own rows, never the shared `entities`. With `MULTI_USER` on, the owner reads these tables too, so **0021 (a copy of the owner's records with the same ids) must be applied before the switch** or the owner's Manage looks empty. With it off, the old global tables are used. The cron backfill is skipped when multi-user is on. A trigger replaces the old foreign keys from events to `entities`.
- **Encrypted companions** (`src/server/entities/people.ts`, `src/services/vaultPeople.ts`): once a vault is on, a person is a `user_entities` row with a random id and `name_encrypted`; the name, notes and aliases are ciphertext, and aliases are HMAC tokens, so the server can merge, repoint and delete people without reading names. Events carry `person_ids`; the browser maps them to names. The server rejects plaintext `notes` or `companions` with 400 once the vault is on. "Convert" turns pre-vault plain people into encrypted ones and erases the plain names, including history. Undo is not offered for vault-person changes and a person merge is not atomic.
- **Genres for members**: your own genres (the ones you set) are in `user_artist_genres` and win in your UI; the shared `artist_genres` stay the owner's.
- **Google Sheets for members** (`sheetRoutes.ts`, `tokenBox.ts`): the `drive.file` scope only; a sheet is made by the app or chosen in Google's picker (`GOOGLE_PICKER_API_KEY`, `GOOGLE_APP_ID`), never linked by pasted URL. The refresh token is sealed with AES-GCM under the Worker secret `SHEETS_TOKEN_ENC_KEY` with the user id as associated data, and kept in the member's `google_sheets` setting. Notes and Went with columns are cut in the browser and again on the server before writing, and from the stored base copy; signing out drops the base. Whoever runs the Worker can still use the token.
- **First sign-in notice** (`NoticeModal`, `/api/me`, `/api/me/notice`): a member accepts the notice once per `NOTICE_VERSION`; it is stored as their `notice_accepted` setting.
- **Response cache**: only Ticketmaster responses, key = hash of host, path and query with the API key removed, 24 hours at most (`0022_cache_ttl_guard.sql` enforces it in the database). Brave is never cached.
- **Quota lanes**: `GEMINI_OWNER_RESERVE=20`, `GEMINI_USER_DAILY=5` interactive, 3 a day per member for backfill round-robin.
- **Checking the token bridge**: `scripts/verify-jwt-mint.ts` mints a 60-second token and checks against the real project that PostgREST reads `auth.uid()` and RLS limits rows to that user. Run it before turning `MULTI_USER` on.

## Activity log and Recently deleted

- Deleting a show moves it to Recently deleted (`logged_events.deleted_at`). Reads skip deleted shows, including Share, CSV import matching and Sheets. Restore clears `deleted_at`. Delete permanently (one show) and Empty recently deleted (all of it, behind a Confirm) erase only rows already in the trash (`eraseDeletedEvent`, `emptyTrash`, `POST /api/events/:id/erase` and `/api/events/trash/empty`); the Log rows for them stay. Undo on a Log row (`src/server/events/undo.ts`, `POST /api/activity/:id/undo`) runs through the store's own methods: an add goes to Recently deleted, a delete or restore swaps back, and a field edit is written back only if the field still holds the value the row logged (otherwise 409 with a reason). Sensitive rows stay disabled until the vault exists. The event panel's History link opens the Log filtered to that show. A nightly job erases trash older than 90 days.
- Every save and delete writes `activity_log` rows: one `create` row, one `update` row per changed field, and `delete` or `restore` rows. Sensitive fields (notes, companions) log that they changed, never the value.
- Undo writes a value back only if the field still holds the value the change wrote (`src/server/events/activityLog.ts`). Notes and companions are sensitive: the Log never prints their text. A notes change keeps its stored ciphertext in the row (only when the vault is on, so plaintext is never logged); companions and plaintext notes keep nothing, so their rows cannot be undone. Undo of a sensitive row needs the vault open: the Log sends `vaultLocked` with the request (missing counts as locked, so the server refuses), and the Log button reads "Unlock vault to undo" while locked. Undoing a sensitive row writes its ciphertext back as stored; no text is decrypted on the server.
- The Log rows are kept one year. Migration 0023 adds both pieces and must be applied before this code runs against Supabase.
